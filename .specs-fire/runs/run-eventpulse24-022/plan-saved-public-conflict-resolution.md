# Implementation Plan: Resolving a conflict that involves a saved public event

**The design is `saved-public-conflict-resolution-design.md`.** This plan is its
implementation sequence — it does not restate the reasoning.

## Approach

The resolve endpoint learns to act on **either** side of a pair, and a new action
**releases a save** rather than deleting a record.

The shape of the change, in one line: **the action determines which side it acts on,
and the server verifies the request names that side.**

- `skip_public` — new `Resolution` value; un-saves a saved side through
  `unsave_event`.
- `edit_new` / `update_existing` — open the **personal** side in the edit sheet.
- `delete_new` — deletes the **personal** side through `delete_personal_event`.
- `keep_both` — mutates nothing; the indicator stays.

The request becomes `side: {kind, id}` instead of `new_side_id`, because "new" is false
for a pair reviewed later on `/conflicts`. The kind is in the request because the
**action**, not the endpoint, decides what a side may be acted on — and the server must
check that the side the client named is the one the action targets.

## Sequence

1. **The enum and the migration.** `SKIP_PUBLIC`; drop and re-add
   `conflict_pair_resolution_kind_ck` with `skip_public` in both kinds' sets.
   `conflict_pair_status_ck` is **unchanged** — a resolved pair carries a non-NULL
   resolution whichever resolution it is.
2. **`unsave_event(..., keep_pair=None)`.** `keep_pair` names one pair to exclude from
   `close_pairs_for_side`. Default `None` preserves today's behaviour exactly.
3. **`conflict_resolutions.py`.** The two maps; the side-in-pair check (today an unknown
   side is silently accepted and yields a resolution with no other side — that becomes a
   refusal); the `skip_public` branch; the parameter renames.
4. **The schemas and the endpoint.** `ConflictSideRef`; `ConflictResolutionIn.side`;
   `ConflictResolutionOut` with `action_side`/`other_side` carrying kinds; `ConflictOut`
   widened to carry both sides.
5. **`conflict_list.py`.** The union for a mixed pair.
6. **`make client`**, then the tests, then the gates.

## The ordering problem, and why `keep_pair` exists

`unsave_event` closes the pairs the save took part in, as `cleared_by_state_change` —
which sets `resolution` to NULL. The resolve service records the resolution **first**
(today's order, kept deliberately: "the resolution is recorded before the action it
names"). So the un-save would overwrite the answer.

The alternative order — un-save first — is worse: the pair would end as
`cleared_by_state_change`, which is **not the user's history** (the previous work item
excludes exactly those pairs from `/conflicts`' Resolved section). The user's answer
would vanish from their history.

So: record the resolution, then un-save with `keep_pair=pair.id`, excluding that pair
from the close. One audit trail per fact: `conflict.resolved` for the answer,
`saved_event.unsaved` for the release.

## The action tables (the source of truth)

`RESOLUTIONS_BY_KIND` (personal side) — **unchanged**:

| Kind | Actions |
|---|---|
| `time` | `keep_both`, `edit_new`, `delete_new` |
| `duplicate` | `keep_both`, `update_existing`, `delete_new` |

`RESOLUTIONS_BY_KIND_SAVED` (saved side) — **new**:

| Kind | Actions |
|---|---|
| `time` | `keep_both`, `edit_new`, `skip_public` |
| `duplicate` | `keep_both`, `update_existing`, `skip_public` |

The **prompt** (the 409) knows the new side's kind and offers that side's set — three
actions, FR-58's "exactly three buttons". The **list** does not know which side the user
will act on, so it offers the **union** across the pair's sides: three for a
personal-vs-personal pair (today's behaviour, unchanged), four for a mixed one.

The resolve endpoint accepts a resolution only if it is in the set **for the side the
request names** — so `delete_new` refuses a saved side and `skip_public` refuses a
personal side.

## Tests

| Test | Proves |
|---|---|
| Every action against both pair shapes | the three personal-side actions and the three saved-side actions |
| An illegal action is refused | `skip_public` on a personal side; `delete_new` on a saved side; `update_existing` on a time pair |
| A side that is not in the pair | refused (today it is silently accepted) |
| Ownership | another user's pair → 404; a side naming another user's record → 404 |
| The already-resolved case | a second resolve → `ConflictAlreadyResolvedError` |
| The migration | forwards on a database holding rows in all three statuses |
| The audit trail | `conflict.resolved` + `saved_event.unsaved`; the pair's resolution is `skip_public`, **not** `cleared_by_state_change` |
| Imported events stay non-deletable | `delete_new` on an imported personal event → `ImportedEventNotDeletableError` |
| The round trip | save → 409 → resolve → the save is gone and the pair is `resolved` with `skip_public` |
| `keep_both` | the pair stays `resolved` and the indicator is kept (FR-58) |

## Technical Details

**Imported events stay non-deletable.** D3's rule is unchanged: an imported event
belongs to the provider, and deleting it would be undone by the next poll. The
refusal happens **before** the pair is marked resolved, so a refused attempt leaves the
pair active and answerable with a choice that works.

**The existing personal-vs-personal behaviour is untouched.** `RESOLUTIONS_BY_KIND` keeps
its shape and its values; the personal set is what the prompt and the list already offer
today. The AC's "existing personal-vs-personal resolutions behave exactly as before" is
satisfied by construction.

**The constraint stops being where the side rule lives.** It never was — it is a
kind-based constraint, and the side shape is only knowable by joining the pair's two
sides. The service narrows it.

**No writes outside the two existing commands.** `delete_new` goes through
`delete_personal_event`; `skip_public` goes through `unsave_event`. There is no third
path to remove a record.

**Migration.** One constraint changed. No column change, no backfill, no data rewrite;
the new set is a superset of the old one for both kinds, so existing rows keep
satisfying it.
