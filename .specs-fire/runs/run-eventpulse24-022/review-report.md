## Auto-Fixed Issues

### 1. [Security] The side lookups were scoped by id only — a pair could read another user's event name

- **File**: `backend/apps/personalization/services/conflict_list.py:216-229`
- **Description**: The **pairs** were scoped to the caller (`filter(user_id=user_id)`),
  but the **side** lookups were scoped by id alone:

  ```python
  personal_events = {
      event.id: event
      for event in PersonalEvent.objects.using(PERSONAL).filter(pk__in=personal_ids)
  }
  saved_events = {
      saved.id: saved
      for saved in SavedEvent.objects.using(PERSONAL).filter(pk__in=saved_ids)
  }
  ```

  The pair row stores its two sides by id. A pair that is the caller's own row names
  two ids — and nothing stopped those ids from naming a `PersonalEvent` or `SavedEvent`
  belonging to **another user**. The lookup would find that row (the id matched) and
  hand its `name` to the caller.

  This was **caught by a test written for the item**, not by inspection:
  `test_the_list_holds_only_the_callers_pairs` failed with
  `assert 'Theirs' not in {'Mine', 'Theirs'}`.

  The fix scopes each lookup to the caller **as well as** to the ids. A side naming a
  row the caller does not own now reads as `available=False` with no name — the same
  explicit "event no longer available" state a deleted side produces, and no leak.

- **Diff**:

```diff
-    personal_events = {
-        event.id: event
-        for event in PersonalEvent.objects.using(PERSONAL).filter(pk__in=personal_ids)
-    }
-    saved_events = {
-        saved.id: saved
-        for saved in SavedEvent.objects.using(PERSONAL).filter(pk__in=saved_ids)
-    }
+    personal_events = {
+        event.id: event
+        for event in PersonalEvent.objects.using(PERSONAL).filter(
+            user_id=user_id, pk__in=personal_ids
+        )
+    }
+    saved_events = {
+        saved.id: saved
+        for saved in SavedEvent.objects.using(PERSONAL).filter(user_id=user_id, pk__in=saved_ids)
+    }
```

  The comment above the block was rewritten to state *why* both filters are needed,
  because the reason ("the pair stores its sides by id, and a row is only the caller's
  if the user id matches") is not obvious from the code alone.

### 2. [Testing] The query-count bound was **vacuous** — it captured the wrong database connection

- **File**: `backend/tests/personalization/test_conflict_list.py` (query bound test)
- **Description**: The acceptance criterion is that the catalog titles come from **one
  batched read for the whole list** — no per-pair query. The test that pinned this
  captured the *default* connection:

  ```python
  with CaptureQueriesContext(connection) as queries:
      result = list_conflict_pairs(user_id=user.pk)
  assert len(queries.captured_queries) <= 1
  ```

  But `PERSONAL = "default"` and `CATALOG = "catalog"` are **two separate Django
  database connections** (verified in `backend/shared/db.py`). The catalog SQL never
  appears on the default connection, so `captured_queries` was `[]` and
  `len([]) <= 1` passed **vacuously**. A catalog N+1 — one query per saved side —
  would have passed every test in the file.

  The project's own pattern confirms the two-alias reality:
  `tests/personalization/test_digest_api.py:615-616` captures `connections[CATALOG]`
  explicitly.

  The fix captures **both** aliases and asserts the catalog count is exactly `1`:

```python
with CaptureQueriesContext(connections[PERSONAL]) as personal_queries:
    with CaptureQueriesContext(connections[CATALOG]) as catalog_queries:
        result = list_conflict_pairs(user_id=user.pk)
assert len(catalog_queries.captured_queries) == 1
```

  **Verified by mutation probe.** The batched read was replaced with a per-side
  lookup; the test then failed with `assert 3 == 1` — the three saved sides cost
  three catalog queries. The change was reverted and the test re-run green.

### 3. [Testing] The ordering test could not distinguish "the earlier side" from "the left side"

- **File**: `backend/tests/personalization/test_conflict_list.py`
- **Description**: The AC says active pairs are ordered by **the earlier side's**
  start time. The service's `_earliest_start()` takes the minimum over the two
  sides' start times — but every fixture in the file was *personal vs personal*, and
  a personal-vs-personal pair always has its personal side on the **left** (the row
  normalises sides on `(kind, id)`, and `personal_event` sorts before `saved_event`).
  So sorting by `left.start_time_utc` and sorting by the earlier side produced
  **identical answers** for every fixture. A mutation to `_earliest_start` returning
  `view.left.start_time_utc` would have passed the whole file.

  A fixture was added in which the **saved** side starts earlier than the personal
  side, and the test asserts the order that follows from the earlier side — not the
  left one.

  **Verified by mutation probe.** `_earliest_start(view)` was changed to
  `view.left.start_time_utc`; the test then failed with the reversed order
  (`['Personal Early', 'Personal Late']` against the expected
  `['Personal Late', 'Personal Early']`). The change was reverted.

### 8. [Architecture] The generated client emitted open `string` types where the file uses closed sets

- **File**: `backend/apps/personalization/schemas.py`
- **Description**: `ConflictPairOut.kind`, `.status` and `.actions` were typed as
  plain `str`, so the generated TypeScript came out as `string` — while the rest of
  the generated schema uses literal unions for every closed set. A client could not
  narrow on `"time"` or `"duplicate"`, and a typo in a kind would be invisible at
  compile time.

  The fix introduces three `Literal` aliases and reuses the `ConflictAction` literal
  that already existed in the file but had **no** references:

```python
ConflictSideKind = Literal["personal_event", "saved_event"]
ConflictPairKind = Literal["time", "duplicate"]
ConflictPairStatus = Literal["active", "resolved", "cleared_by_state_change"]
```

  `ConflictPairOut.kind` is now `ConflictPairKind`, `.status` is `ConflictPairStatus`,
  and `.actions` is `list[ConflictAction]`. The regenerated client now emits
  `kind: "personal_event" | "saved_event"` and the matching unions for kind, status
  and action.

## Auto-Fixed Issues

### 1. [Architecture] An action could be offered against a side it cannot act on

- **File**: `backend/apps/personalization/services/conflict_resolutions.py:294-302`
- **Description**: `RESOLUTIONS_BY_KIND_SAVED[DUPLICATE]` contained `update_existing`,
  and `RESOLUTIONS_BY_KIND_SAVED[TIME]` contained `edit_new`. But both of those actions
  open the **personal** side in the edit sheet — a save has no edit sheet. So the
  "actions legal against a saved side" set was not the set of actions that *act* on a
  saved side, and the server accepted `update_existing` naming a saved side. The client
  was offered a choice that did nothing.

  The fix introduces the rule the design had not stated — **an action names its own
  target** — and checks the named side against it:

  ```python
  def _target_side_kind(resolution: str) -> str:
      if resolution == ConflictPair.Resolution.SKIP_PUBLIC:
          return ConflictPair.SideKind.SAVED_EVENT
      return ConflictPair.SideKind.PERSONAL_EVENT
  ```

  and in `resolve_conflict`:

  ```python
  if value != ConflictPair.Resolution.KEEP_BOTH and side_kind != _target_side_kind(value):
      raise IllegalResolutionError(...)
  ```

  `keep_both` acts on neither side, so either of the pair's two sides may be named; every
  other action demands exactly one kind of side. **The two checks are complementary, not
  redundant** — the first asks "is this action in the menu the server offers?", the
  second asks "does this action act on the kind of side named?". The combination was
  traced across all 12 (kind × side-kind × action) combinations and every one is either
  accepted or refused for a stated reason.
- **Severity**: Medium — a client could offer a choice that did nothing.
- **Status**: **Fixed.** Proved by `test_a_duplicate_pair_with_a_saved_side_refuses_update_existing_on_the_saved_side`,
  which failed before the fix ("DID NOT RAISE") and passes after.

### 2. [Testing] The migration test wrote an illegal resolution against a TIME pair

### 3. [Testing] A pre-existing index test was a coin toss, not a rule

- **File**: `backend/tests/personalization/test_digest_models.py:590`
- **Description**: `test_the_most_recent_composition_lookup_uses_the_index` asserted on
  the query plan Postgres **chose**. On a table with three rows the cost model
  legitimately prefers a sequential scan, so which way it fell depended on the table's
  statistics at that moment — the test failed roughly one run in two under `--cov`, and

- **Severity**: Low — but it made the gate run unreliable for the rest of this run.
- **Status**: **Fixed** by asking the question the test means to ask. The plan is now
  taken with `enable_seqscan = off`, so the planner must use an index if one applies:

  **Proved not vacuous with a mutation probe**: the index was removed from the model,

  planner fell back to a *different* index, which is exactly what the assertion catches.
  The probe was then reverted: the model restored, the migration unapplied and deleted,
  and `makemigrations --check` reports no changes.

## Auto-Fixed Issues

### 1. [Architecture] The indicator measured the **block's own span** instead of the **pair's overlap**

- **File**: `backend/apps/personalization/services/timeline.py`
- **Description**: The AC says the indicator "fires on the day-cell whose interval
  contains **the overlap**". The first implementation ANDed the conflict flag with
  `overlaps_day()` tested against the **block's own** interval — so a personal event
  running Friday 22:00 → Saturday 02:00 that clashes only on Friday lit **both** Friday
  and Saturday. The clash is between the two *conflicting* events; it is not the block's
  whole span.

  The fix introduces the window the pair actually occupies:

  ```python
  @dataclass(frozen=True)
  class _ConflictWindow:
      start_utc: datetime
      end_utc: datetime | None

  def _side_window(*, start_utc, end_utc, other_start_utc, other_end_utc, kind):
      if kind == ConflictPair.Kind.TIME:
          start = max(start_utc, other_start_utc)
          ends = [end for end in (end_utc, other_end_utc) if end is not None]
          end = min(ends) if ends else None
      else:
          start = min(start_utc, other_start_utc)
          ends = [end for end in (end_utc, other_end_utc) if end is not None]
          end = max(ends) if ends else None
      return _ConflictWindow(start_utc=start, end_utc=end)
  ```

  A **time** pair's window is the intersection of the two sides' intervals. A
  **duplicate** pair has no intersection to take — its two sides are the same event
  twice — so its window is the span the two sides share, which puts the indicator on
  the day the duplicate actually sits. The block's own days still come from the
  block's own span; only the flag moves to the pair's window.
- **Severity**: High — this is the difference between "the clash is on Friday" and
  "the event is on Friday and Saturday".
- **Status**: **Fixed.** Proved by
  `test_the_indicator_lights_only_the_day_cell_that_contains_the_overlap`, which failed
  before the fix (Saturday's cell carried `conflict=True`) and passes after.

### 2. [Testing] The open-ended event covered only its start day

- **File**: `backend/apps/personalization/services/timeline_days.py`
- **Description**: `days_covered()` set `last = first` when `end_utc is None`, so an
  event with no end appeared on **one** day — contradicting its own docstring, which
  says an open-ended event "runs from its start onward" and therefore covers every day
  after it. The week read would have shown a multi-day open-ended event as a single
  block.
- **Fix**:

  ```python
  if end_utc is None:
      # An open-ended event has no end to convert, so there is no last day to read off
      # it. It runs from its start onward — which means it covers **every** day from
      # its start to the limit. With no limit there is no day after the start to name,
      # so it covers its start alone.
      last = limit if limit is not None else first
  ```
- **Severity**: High — a whole class of events was placed on the wrong days.
- **Status**: **Fixed.** Pinned by
  `test_an_open_ended_event_appears_on_every_day_of_the_week_from_its_start`.

### 3. [Testing] `days_covered()` truncated the last day of its range

- **Severity**: Medium — the last day of every range was silently missing.
- **Status**: **Fixed.** Pinned by

### 8. [Code Quality] The pair-side helper was re-read from the tables, breaking the query budget

## Findings

### 1. [Architecture] The panel synchronised a prop into state through an effect

- **File**: `frontend/components/personal-events-panel.tsx`
- **Description**: The first implementation copied `editingEventId` into a `useState` in
  a `useEffect`, so the sheet could be driven from the Timeline. That is two sources of
  truth for one fact, and a render between the effect and the state would show the
  **wrong event** in the edit sheet — the user would be editing one event while the UI
  showed another's values.

  `react-hooks/set-state-in-effect` flagged it, and the rule was right. The state is now
  **derived during render**:

  ```tsx
  const driven = editingEventId !== undefined;
  const drivenEvent = driven
    ? (editingEvents.find((candidate) => candidate.id === editingEventId) ?? null)
    : null;

  const editing = driven ? drivenEvent : ownEditing;
  const formOpen = driven ? drivenEvent !== null : (createOpen ?? ownFormOpen);
  ```

  There is no effect, and the two paths agree: a caller that clears the id is closing the
  sheet, and the sheet's own "Cancel" clears the id through the same callback. The form's
  key follows the driven event (`driven-${editing?.id ?? "none"}`), so naming a second
  event remounts the form with that event's values rather than carrying the last one's.
- **Severity**: High — a wrong event in the edit sheet is a data-loss bug.
- **Status**: **Fixed.** The effect is gone; `useEffect` is no longer imported.

### 2. [Code Quality] The block's time line named the zone twice

- **File**: `frontend/components/timeline/timeline-block.tsx`
- **Description**: `cardTime` prints a time with the zone's short name inline — "Mon,
  Nov 2 · 9:00 AM EST". The range built itself by keeping the start's string whole and
  appending the end's clock, so the zone appeared **twice**: "Mon, Nov 2 · 9:00 AM EST –
  10:30 AM EST". The design says the zone appears once, at the end.

  The range now strips both ends' inline zones and prints the zone once:

  ```
  Mon, Nov 2 · 9:00 AM – 10:30 AM EST
  ```
- **Severity**: Medium — a duplicated zone is noise on the densest surface in the app.
- **Status**: **Fixed.** Pinned by `timeline-panel.test.ts` → "prints the range, with the
  zone named once", which asserts the exact string.

### 3. [Code Quality] `blockTime` built a regular expression from the zone's name

- **File**: `frontend/components/timeline/timeline-block.tsx`
- **Description**: The zone was stripped with
  `endClock.replace(new RegExp(\` ${zone}$\`), "")`. The zone's short name is a
  **rendered string** — whatever the platform's `Intl` reports — so it would have to be
  escaped before it could go into a pattern. A name carrying a metacharacter would
  either throw or strip the wrong text.

  The zone is now **counted off the end** of the string, which cannot go wrong.
- **Severity**: Medium — a latent crash or a silently mangled time.
- **Status**: **Fixed.** Pinned by "does not build a pattern from the zone's name".

### 4. [Architecture] The Timeline's blocks were mapped to personal events with a fabricated `version: 1`

- **Files**: `frontend/components/timeline/timeline-panel.tsx`,
  `frontend/components/personal-events-panel.tsx`
- **Description**: `PersonalEventOut` carries `version` — the optimistic-locking counter
  — and the Timeline's block payload does **not**. The mapping filled it in with `1`,
  which is an invented fact about the event. It happened to be inert (the edit body
  carries no version, and `seedFrom` does not read it), but it is exactly the kind of
  fabricated value that becomes load-bearing the moment somebody reads it.

  The panel's `editingEvents` prop now takes a **narrow `PersonalEventSeed`** — the id,
  name, times, zone, location and notes, and nothing else:

  ```tsx
  export type PersonalEventSeed = {
    id: string;
    name: string;
    start_time_utc: string;
    start_time_tz: string;
    end_time_utc?: string | null;
    location?: string | null;
    notes?: string | null;
  };
  ```

  A caller holding a full `PersonalEventOut` still passes one unchanged — it satisfies
  this type by having more. The conflict sheet's two `openEdit` calls dropped their
  `version: 1` for the same reason; the zone stays empty there because the 409 payload
  does not carry one, and the sheet falls back to UTC rather than showing a zone it was
  never told.
- **Severity**: Medium — a fabricated fact in the data layer.
- **Status**: **Fixed.** `tsc` is clean and the suite is green.

### 8. [Code Quality] `mondayOf` existed in two places

- **Files**: `frontend/app/timeline/page.tsx`, `frontend/lib/timeline-dates.ts`
- **Description**: The page's "Today" control needs the Monday of the **current** week;
  the dates module needs the weekday of a **calendar date**. They are related but not

taking over the failure message too, or a refused save would close the sheet in silence.

# Review: e2e-proof-and-contract-tests

## What was built

**A backend scenario that drives the HTTP stack** — not the services — through the
whole `timeline-and-conflicts` intent in one path: save a public event that clashes with
one of the user's own events, read the week, read the conflict list, resolve the pair,
read the week again. Twelve tests, and each one is named after the rule it pins.

**A mutation-probe harness** with eight probes, one per named rule: the cross-midnight
indicator, the Timeline's ownership, the conflict list's ownership, keep-both keeping the
flag, the action naming its own target, a closed pair being immutable, the Timeline read
going through the generated client, and a call site's path being in the committed schema.
Each probe plants one real bug — code that still parses and still runs — and requires the
suite to **fail**. The file is always restored in a `finally`, and a probe whose pattern
does not apply reports `SKIP`, which is treated as a failure.

**One new direction in the contract sweep.** The existing test went schema→client: it
checked that every operation in the schema has a caller. The new check goes
call-site→schema: it walks the source tree, finds every `api.GET`/`POST`/`PATCH`/`DELETE`,
and asserts each path is in `openapi.paths`. It is derived from the tree, not from a
hand-kept list, so a new call site cannot quietly escape it. The `caller` field became a
**list**, because the resolve endpoint has three call sites and one of them would
otherwise have been invisible.

## The decisions, and what held up

- **D1 — the scenario drives the HTTP stack.** The 409 *is* the seam. A service-level
  call cannot observe a 409 at all, and the 409 is where the pair id first appears. This
  held up: the scenario can assert that the pair id in the 409 is the pair id in the list
  is the pair id in the resolve response — a chain that no service-level test can see.
- **D2 — the pair is created by a real clash**, not a hand-written row. A hand-written
  pair proves the read; a real clash proves the whole path, including that the pair is
  created by the thing that should create it. This held up, and it is why the save row's
  id and the catalog event's id are provably different.
- **D3 — the week is named by any date in it**, not just the Monday. The client links to a
  week; asking for a Wednesday and getting the Monday's week is the behaviour that
  matters. Held up — the test asks for seven different dates and gets the same week back.
- **D4 — isolation is one test, two users, at the point the first user's pair is
  *active*.** Proving isolation after a resolution would be proving it about a different
  state. The active state is where a scoping bug would leak.
- **D5 — the probes target the rules the acceptance criterion names**, and each mutation
  still parses. This held up, and it is where the item's most valuable finding came from.
- **D6 — `make client` is verified by a diff**, not a test. A test would have to
  generate the client and compare it, which is the diff. The diff is the check.

## Findings

**1. The resolve service's safety property rests on the allowed-set check alone.** The
service has two guards: the membership check against `resolutions_for_side`, and an
explicit `side_kind != _target_side_kind(value)` comparison. The second is **unreachable**
— the allowed set already excludes every mismatched pair — so removing it changes
nothing and the suite stayed green. The first probe aimed at that guard proved nothing
about the rule. This is not a hole in the tests; it is a finding about the implementation.
The probe was re-aimed at the check that actually carries the property, and the redundant
guard was **left in the code**: it is a correct statement of the rule, and removing it
would change reviewed code for no gain.

**2. Two pre-existing lint failures, in files the *previous* item touched.**
`detail_conflict.py:158` was a 101-character line, and `test_detail_conflict.py:31`
imported `SavedEvent` without using it. Both had been reported green when the previous
item finished, which means the previous item's gate run did not catch them. Both are now
fixed, and `ruff format .` reformatted three files as a side effect.

**3. The `week` link's Monday** was proved by asking for a Wednesday. The client's link
carries a date, and the server resolves it to the containing week. Asking only for the
Monday would have passed against an implementation that ignored the date entirely.
