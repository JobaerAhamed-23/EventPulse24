## Auto-Fixed

### 1. [Code quality] The focus trap's docstring described a handler that was not there

**File:** `frontend/components/settings/account-delete-modal.tsx:188`

The comment read *"The trap is a `keydown` handler on the panel rather than a global
one, so it only runs while the panel is mounted."* **The handler is on `document`**,
not on the panel.

**Why the code is right and the comment was wrong:** the browser moves the focus itself
and the `keydown` still fires on whatever now holds it — which may be the body's last
descendant rather than the panel. A listener on the panel would miss the very case the
trap exists for. The listener *is* removed when the modal closes, so the comment's
intent — "it only runs while the panel is mounted" — was already true.

**Fix:** the comment now says what the code does and why the document is the right
target.

### 2. [Testing] Two off-scale spacing utilities

**File:** `frontend/components/settings/account-delete-modal.tsx`

`mt-5` and `pt-5` generate **no CSS at all** in this project — `tokens.css` resets
Tailwind's spacing multiplier and declares only DESIGN.md's steps (0, 1, 2, 3, 4, 6, 8,
12, 16, 20, 30). A dialog with those classes would have had a button with no padding
above it and no padding below the rule.

Caught by `tests/spacing-scale.test.ts`, which the full suite ran. **Fixed** to `mt-6`
and `pt-6`, both on the scale.

## Accepted as Correct

These are decisions, not defects. Each was checked against the code and the standards,
and each is recorded because a reviewer should be able to disagree with it.

### Code quality

1. **The modal's `FOCUSABLE` selector asks the DOM rather than keeping a list.**
   A hard-coded list of the panel's focusable elements would go stale the moment a
   button was added, and the trap would then hold the wrong edges. **The DOM is the
   only honest source.**

2. **`value === CONFIRM_WORD` — no `.trim()`, no case-fold.**
   A trimmed comparison would let `" DELETE "` through, which *looks* strict and is not.
   Both failure modes are covered by separate tests, because one test cannot hold both
   claims.

3. **The primary button says "Start 30-day deletion", not "Delete account".**
   The engine *schedules*; it does not delete on this call. **The label tells the truth
   about what the button does.** The hardcoded "30" in the label is A-16's own string
   and is not a duration the frontend computes — the *date* is the server's, and it
   arrives in `scheduled_for`.

4. **The backdrop is a sibling of the panel, not a wrapper.**
   A click on a wrapper that contains the dialog is a click *on the dialog*. As a
   sibling, the click is outside, which is what closes it. **The same shape
   `components/digest/mute-prompt.tsx` uses.**

5. **The disabled primary's treatment has no precedent in the repo** — no existing
   primary button is ever disabled. **A-16 specifies it** (`bg-surface-inset`,
   `text-ink-faint`, `cursor: not-allowed`), and both tokens exist.

### Security

6. **The copy endpoint is behind the same session wall as the thing it previews.**
   `current_user(request)` is called and its result discarded — the resolver raises for
   an anonymous caller, and **that is the point of the call**. The two strings describe
   what the engine does and are the same for everybody, so the account's own state is
   not in the answer.

7. **A `GET` needs no CSRF token, and the code says why.** CSRF guards writes; a read
   that changes nothing is not something an attacker could act on.

8. **Nothing personal reaches the copy.** The preview carries two product-level
   sentences and no user data, so the response cannot leak anything about the caller.
   `test_the_preview_changes_nothing` also proves it writes no `DeletionRequest`.

### Architecture

9. **The container owns the modal's open state; the modal owns everything inside it.**
   The container already owns `pending` and `kept`, and it is the thing that knows
   whether a deletion is pending — **a modal in front of a pending deletion would be
   offering a second request for something already asked for.** The modal owns the
   input, the gate, the focus trap and the request.

10. **The container does not fetch anything, and does not `router.refresh()`.**
    `router.refresh()` is the project's pattern for a write that changes
    server-rendered state — but here the container already holds the answer:
    **the endpoint returns `scheduled_for`**, and a refresh would be a second round
    trip for a value the client is already holding.

11. **The copy is fetched when the section mounts, not when the modal opens.**
    A dialog that had to load before it could say anything would put a spinner in
    front of the one screen a person reads before destroying an account.

12. **The modal renders only when the copy is there.**
    A dialog with two blank paragraphs in it would say nothing about what is about to
    happen — **which is the one thing it exists to say.** The test
    `does not open the modal when the copy could not be read` holds that.

13. **The modal is a sibling of the section's content, not a child of the row.**
    The row unmounts when the request lands, and a dialog that lived inside the row
    would unmount with it — taking the pending state it had just asked for.

14. **`AccountDeletionCopyOut` is a base schema, and `AccountDeletionRequestOut`
    inherits from it.**
    The two endpoints publish the same two fields, and the inheritance is what makes
    "the same two strings" structural rather than a convention.

### Testing

15. **The backend test asserts the copy is *true of the engine*, not merely published.**
    `test_the_first_paragraph_names_what_is_actually_purged` runs `purgeable_models()`
    and checks each of the three families the paragraph names is on the list — **so a
    copy that named a family the engine does not purge would fail.**

16. **`test_neither_paragraph_claims_the_deletion_cannot_be_reversed` holds the one
    claim the copy must not make.** The A-16 mockup's ¶2 ends *"We can't reverse
    deletion."*, which contradicts ¶3's grace period in the very next paragraph. **The
    mockup's wording is not what ships.**

17. **The `POST` exemption was deleted, not rewritten.** A rewritten exemption would
    be a second sentence about an endpoint that now has a caller — and
    `tests/endpoint-coverage.test.ts`'s own *"has no declared-uncalled endpoint that
    is in fact called"* check would then fail it.

18. **The trap's companion test — `lets an ordinary Tab pass through the middle of the
    dialog` — is what stops the trap from being a blunt instrument.** A trap that
    swallowed every Tab would break the dialog rather than contain it, and it would
    also pass a test that only checked *"the trap exists"*.

## Needs Confirmation — one finding

### [Architecture] After a successful request, the focus lands on nothing

**File:** `frontend/components/settings/danger-zone.tsx:197`

**The modal's own failure behaviour is correct.** When the request fails, the input's
value is preserved, the primary re-enables, the focus is still on it, and the
`role="alert"` announces the refusal — the message and the control it belongs to
cannot be separated. Nothing is wrong here.

**The finding is about the section, and it is about success.** When the request
*succeeds*, the container moves the section to the pending state — **the row that held
the "Delete account →" button unmounts, and with it the element that had the focus.**
The reader is dropped to the top of the document.

**This is the same asymmetry recorded in item 3's review report**: the reassurance's
live region is outside the row, and the row unmounts on success, so the same thing
happens on the cancellation path. **The two paths have the same shape.**

**Why it is not fixed here.** Moving the focus to the pending row is a real
behavioural decision about the section's focus management, and it applies to the
cancellation path as much as to the deletion path. **Changing it inside this item
would be a silent behavioural change to a surface item 3 already shipped and
reviewed.** It is recorded here so the decision is visible rather than lost.

**The cost of not fixing it now:** a keyboard user who completes the deletion is
dropped to the top of the document. **The cost of fixing it now:** a focus-management
change to a shipped surface, made silently, in an item about a modal.

**Suggested follow-up:** a work item for the danger zone's focus management on
success — covering both the deletion path and the cancellation path together, since
they have the same shape.

## The One Deliberate Departure From A-16

**A-16's ¶1 and ¶2 are not shipped, and the backend's canonical strings are.**

| ¶ | A-16's mockup | What ships | Why |
|---|---|---|---|
| 1 | *"We'll permanently delete your account, personal events, saved events, and preference graph within **30 days**."* | `DELETION_REMOVES` — *"Your personal events, your saved events, and your preference graph — the taste we built up about what you like."* | The nouns are right; the **verb is not**. "Permanently delete … within 30 days" says two things at once and neither is the engine's: nothing is deleted *within* the grace period, and the deletion is not permanent at request time. |
| 2 | *"**Anonymized aggregates** … survive. **We can't reverse deletion.**"* | `DELETION_SURVIVES` — *"Anonymised aggregate figures survive … They are not linked to your account and cannot be traced back to you."* | The mockup's sentence is **half a promise the engine does not keep** — "We can't reverse deletion" contradicts the grace period *in the very next paragraph*. |
| 3 | *"You can cancel anytime during the 30-day grace from this page or from the email we send."* | **Verbatim.** | True, and shippable as written — item 1 shipped the mail and item 3 shipped the cancel surface. |

**The backend's wording already existed and already ships in the mail.** Using it is
what makes the modal and the mail the same sentence rather than two.

## A Note on the Test That Survived Its Mutation

Recorded in the test report at length, and it is the most useful thing this review
found: **the first version of the modal's failure test mocked `onClose` and never
inspected the mock**, so a modal that closed itself on a failed request passed. The
gap was closed by asserting `onClose` was not called.

**The general form of it:** a test that mocks a collaborator and then never inspects
the mock is testing half the contract. `onRequested` was already asserted with its
argument; `onClose` was not, **and the difference is exactly where the bug was.**
