## What the review found

**Four defects, all confirmed against the live database rather than reasoned about.**
Every one was reproduced by running it, and every fix was confirmed by a mutation
probe that now fails.

### 1. The purge was barely tested — **High**

**The file's own docstring claimed "The purge is thorough. Every categorised row is
gone", and the only row any test asserted was gone was the `DeletionRequest`** — the
one model the purge is least likely to get wrong, because it has a plain `user_id`
column like most of them.

**The probe: the purge loop replaced with `pass`.** One test failed. The other 28
purged models — `personalization.savedevent`, `personalinterest`, `reminderplan`,
`calendarconnection`, `passwordresettoken`, `delivery.scheduledsend` and twenty more —
could all silently survive a person's deletion with the suite green.

**Fixed.** A new test asserts the *awkward* cases rather than the easy one:

- `Interest` — a plain `user_id`, in `personalization`;
- `SavedCollectionItem` — **no `user_id` at all**, reached through
  `collection__user_id`. A walk that forgot the traversal would leave it behind,
  holding a save that outlived the account.

**And it asserts the other side of the same purge: another account's rows survive.** A
purge that is too narrow is a bug; one that is too wide is a worse one. The probe now
catches both — a no-op purge fails two tests, and an unscoped purge fails the
"theirs survived" half.

### 2. A store failure escaped the commit callback — **High**

**The picture's object is removed in `transaction.on_commit`, after the transaction has
committed.** At that point the account is already gone and there is nothing left to
undo — so a failure there is a *leak*, not an error. The module says so, and the
docstring says so.

**It was not so.** `_delete_object_quietly` caught only `BlobError`, and the callback
was registered without `robust=True`. Two realistic triggers are not `BlobError`:
`get_adapter` raises `ImproperlyConfigured` when `settings.ADAPTERS` names an adapter
that is not registered, and the port's key validation raises `ValueError`.

**The consequence is worse than a leak.** The exception escaped `destroy_account`
*after* the account had been fully destroyed, so the worker caught it and logged
**"Account not destroyed"** — for an account that *was* destroyed. The operator's log
lied about what happened.

**Fixed.** `robust=True` on the registration — the structural belt — plus a broad
`except` in the cleanup — the first belt. **Two tests, because the two layers are not
distinguishable by outcome:** removing either one alone leaves the other holding the
promise, so the outcome test alone would pass against a half-fix. The structural test
replaces the cleanup *wholesale* with one that raises, which only `robust=True` can
absorb.

### 3. A model was classified as surviving and could not be — **High**

**`admin.logentry` is `AUDIT_LOG`, so by category it survived.** And it cannot: its
`user_id` is `NOT NULL` with a foreign key to `User`, so the row is **structurally
impossible** to keep once the account is gone. The constraint is deferred, so the
failure lands at commit.

**And the account row was deleted in the middle of the walk.** `purgeable_models()`
sorts by label, so `identity.user` landed at position 10 of 29 — before the
seventeen `personalization` models and before the audit row for the deletion was even
written. The module's own docstring said *"the account last"*; the code did the
opposite.

**Fixed, in two parts.** `User` is excluded from `purgeable_models()` and deleted by
hand at the end — the ordering the docstring promised, now asserted by a test. And
`admin.logentry` is named in `PURGED_MODEL_OVERRIDES` **with its reason**, because the
schema forbids the survival its category implies.

**This is not a hole in the audit trail.** Django's admin is off in this project —
`apps/ingestion/admin.py` says so outright: *"admin's `LogEntry` is off: the
`IngestionAuditEntry` each command writes is the only history."* The audit log that
matters is `identity.identityauditentry`, which is append-only, carries no PII, and
survives by name — and a test asserts it does.

**The override table now carries reasons, like `SURVIVING_MODELS` does.** A bare
`frozenset` would have let the two layers disagree silently, which is the exact defect
that `SURVIVING_MODELS` was changed to prevent in the first place. Three new tests
assert the override's reason is present, that its names are real models, and that the
two layers agree.

### 4. A test asserted the opposite of its name — **Medium**

`test_a_cancelled_request_is_not_destroyed_after_the_grace_period` called
`destroy_account` **directly** and asserted the account **was** destroyed. Its name
said the opposite, and a reader would trust the name.

The behaviour it describes was real — cancelling does stop the destruction — but it is
a property of the *worker's due-list*, and the worker was never invoked. **Rewritten**
to assert what its name says, with the worker-level behaviour asserted where the
worker is the thing under test, in `tests/worker/test_account_deletion_task.py`.

## Judgment calls worth recording

| Decision | Why |
|---|---|
| The object is removed at **destruction**, not at request | The grace period is a written promise. Deleting the object at request makes it a lie: the user cancels and their face is gone. The cost — the bucket holds a picture for thirty days after the ask — is paid deliberately. |
| `destroy_account` does **not** check for a pending request | The grace period is enforced by the worker, which feeds the command only what is due. The command is the hammer; `due_deletion_requests` is the gate. **The docstring said otherwise and was corrected** — see the suggestion below. |
| `PURGED_MODEL_OVERRIDES` became a `dict[str, str]` | A bare set of names lets the per-model and category layers disagree without anybody noticing. The same reasoning that changed `SURVIVING_MODELS`. |
| The account row is deleted by hand, not by the walk | The walk sorts by label, and `identity.user` sorts into the middle. The ordering is a promise; the sort is an implementation detail. |
| `admin.logentry` is purged, not survived | The schema forbids it. A classification the database will not permit is a lie waiting for the worst possible moment. |
| The A-16 modal is not built | A type-to-confirm modal is a promise made in the product's voice. Two of A-16's three paragraphs would describe behaviour that does not exist. **A modal in front of promises the engine does not keep is worse than no modal.** |
| The anonymised aggregates are not produced here | They come from the analytics pipeline, and no aggregate row carries a user id — so they survive by having nothing to link them to. A fact about the pipeline, not an omission. |

## Suggestions requiring approval

**One.** It is a behaviour change, so it is not auto-fixed.

### 1. [Architecture] Should `destroy_account` refuse an account that never asked to be deleted?

**File**: `apps/identity/services/deletion.py:475`

**The situation.** `destroy_account` destroys the account it is given, without checking
that a deletion was requested. Its docstring used to promise `False` for "no pending
request"; the code never did that, and the docstring now says the grace period is the
worker's job.

**Why it matters.** The command is exported from `apps/identity/services/__init__.py`,
so any future caller can destroy an account unilaterally. Today the only caller is the
worker, which feeds it only what is due — so there is no live path. But the safety
property is not enforced anywhere; it is a convention, and conventions are what
disappear.

**The two options.**

| Option | What changes | Cost |
|---|---|---|
| **(a) Keep the hammer** | Nothing. The docstring already says the gate is the worker's. | The safety is a convention. A future caller can destroy an account with no request. |
| **(b) Require a pending request** | `destroy_account` returns `False` when there is no pending `DeletionRequest`. | Eight test call sites need a request first. And the *worker* would need to pass the request, or the check would have to accept a `force` flag — which reopens the same door. |

**Recommendation: (a), as it stands.** The reason is that option (b)'s safety is
illusory: the worker destroys accounts *because* they are due, and the request row is
deleted by the purge itself — so the check has to be "was there a request", not "is
there a request now", and the command would need to be told which request it is
honouring. That is more machinery than the risk warrants, and it would put the real
guarantee (the worker's due-list) one layer further from the reader.

**What would change the recommendation**: a second caller of `destroy_account` that is
not the worker. If one appears, (b) becomes worth its cost.
