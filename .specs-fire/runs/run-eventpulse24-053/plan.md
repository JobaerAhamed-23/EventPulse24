# Implementation Plan: Deleting an Account — and the Picture That Must Not Outlive It

**Design document:**
`.specs-fire/intents/account-profile-expansion/work-items/account-deletion-and-avatar-removal-design.md`

## Approach

Follow the approved design exactly.

1. **The grace period is a row.** `DeletionRequest` on `identity` holds `user_id`,
   `requested_at` and `scheduled_for`. Cancelling deletes the row, and the account comes
   back whole — including its picture, because the object was never removed.
2. **Three named commands** in `apps/identity/services/deletion.py`:
   `request_account_deletion`, `cancel_account_deletion`, `destroy_account`. AD-5 is
   honoured — no write in the API layer.
3. **The retention walk classifies by category, not by model name**, with three
   per-model exceptions (`identity.identityauditentry` survives;
   `identity.subscription` survives; `personalization.savedcollectionitem` is reached
   through `collection__user_id`). The classification is **asserted against
   `retention_registry()`** so a model added later fails the build rather than silently
   surviving.
4. **The picture's object is removed in `transaction.on_commit`, when the account is
   destroyed** — not when deletion is requested — and **only if the key is non-empty**,
   because `delete("")` raises `ValueError` from the port's key validation.
5. **The purge session setting is set inside the transaction.** `SET LOCAL
   eventpulse.retention_purge = 'on'` is what the append-only triggers already expect;
   no production Python sets it today, and this is the first code that does.
6. **Audit rows survive the account.** They are append-only and AD-13 keeps PII out of
   them precisely so they can outlive the person. `destroy_account` writes its own row
   before the `User` row goes.
7. **The A-16 modal is scoped to a follow-up item** and the work item is updated to say
   so. The API it needs exists in this pass.

# Implementation Plan: The Face, Everywhere the Name Already Is

**Work item:** `avatar-on-the-shell` (confirm mode) · **Intent:** `account-profile-expansion`
**Depends on:** `avatar-endpoint-and-contract` (the API and the generated client)

## Approach

**The picture goes where the display name already goes.** `AppShell` passes `name` and
`email` to `Sidenav` and `BottomTabNav`; the avatar follows the same path rather than
inventing a second one. The three places — the sidenav's account row, the bottom bar's
More sheet, and the account sheet — all render `AccountPanel`/`AccountMenu`, so there is
**one** place the disc is drawn and it is drawn three times.

**The fallback must not blank anything.** The initials rule lives in **one** module,
`frontend/lib/avatar.ts`, mirroring `frontend/lib/display-name.ts`: the initials of the
display name, capped at two letters, never empty (a display name is never empty). The
disc renders the picture when there is one and the initials when there is not — and the
**name beside it is never blanked**, because the name is rendered as text regardless of
the picture's state.

**The upload control is not save-on-change, and that is the honest break with the house
pattern.** A file picker has a moment — the file is chosen — and that moment is the
save. There is no undo on a file picker, so the screen says what will happen before it
happens rather than after. The control is a real `<input type="file">` behind a
labelled button, with `accept` set to the formats the server allows.

**The shell follows the save, as the name does — and never before.** The shell is
rendered on the server, so the picture it was drawn with is fixed for the life of the
render. **A save that does not show up is a save that did not happen.** The precedent is
`publishName` in `frontend/lib/session-name.ts`, and the avatar publishes the same way
after the server has accepted the write — **never before**, because the server may refuse
the file.

**The avatar gets its own channel, and here is why.** `session-name.ts` publishes a
*string*; the avatar publishes a *URL*, and a URL has two properties the name does not:
it changes when the picture is replaced (the `{version}` segment), and it becomes `""`
when the picture is removed. Reusing the name's channel would mean publishing a URL
through a store typed `string | null` whose `null` means "ask the seed" — and the
seed for a picture is a *different* question from the seed for a name. **Two channels,
two stores, one rule each**: `null` means "ask the seed", and the seed is what the page
was rendered with.

**The signed URL cannot expire on screen, and that is why the URL is stable.** The
storage design chose an app-owned URL (`/api/auth/profile/avatar/{version}`) that 302s
to a freshly-minted presigned URL. The browser sees the stable URL and the redirect
happens under it, so a signature that expires while the page is open is re-minted on the
next request. **A broken image icon in the rail is not an acceptable answer**, and this
is the answer: the URL the shell carries never carries a signature.

**The image carries alt text that is not the word "avatar".** The name is already beside
the disc in text, so the image is `alt=""` — **decorative** — and the disc keeps its
`aria-hidden`. A screen reader reads the name once, not "avatar, Maya Ahmed".

**The failure line is the API's own, verbatim**, through the same `saveFailureMessage`
helper `profile-name.tsx` uses. The generic offline line appears only when the request
never reached the API.

## Technical Details

- **The `me` field is `avatar_url`, and it is `""` when unset** — not `null`, not
  absent. `CurrentUserOut.avatar_url` already carries it (AD-19, the endpoint item).
- **`useLiveAvatar(seed)` is the seed-or-published rule**, exactly parallel to
  `useLiveName(seed)`. `null` means "ask the seed"; the seed is what the page was
  rendered with.
- **The in-flight counter is a ref, not state** — `saves.current` — so a late response
  cannot overwrite a newer picture and a second upload cannot be started into two
  orphaned objects (the work item's own hazard).
- **The control is not pressable twice**: the file input is `disabled` while an upload
  is in flight, and `aria-busy` is set on the region.
- **No `next/image`.** The URL is same-origin (`/api/auth/profile/avatar/{version}`), so
  the plain `<img>` needs no remote allowlist in `next.config.ts`. The work item flagged
  the allowlist as a thing to check; the measured answer is that it is not needed, and
  `next.config.ts`'s docstring records that.
- **The file input is visually hidden but not `display: none`** — a `display: none`
  input cannot be triggered by a label in some browsers, and it drops out of the
  accessibility tree. It is `sr-only` and the button is the real control.

# Implementation Plan: One Screen That Holds All of It — and an e2e That Clicks Through

**Work item:** `profile-screen-and-e2e` (confirm mode) · **Intent:** `account-profile-expansion`
**Depends on:** `avatar-on-the-shell`, `email-change-on-the-profile-screen`,
`place-on-the-profile-screen` — all completed.

## Approach

**This is the integration item, and it starts by finding out what is already true.**

**The screen is already composed.** `app/settings/profile/page.tsx` already renders
`AvatarUpload`, `ProfileName`, `EmailChange` and `HomeCity` — the four parts are on it,
in that order, and the three earlier items in this intent each landed their part. **So
requirement 2 ("the screen renders name, picture, email and place as one coherent
profile") is largely a question about the *order* and the *docstrings*, not about new
markup.**

**The docstrings are the actual work, and they are not a formality.** The screen's
rationale still argues for a design the code no longer has:

- *"It shipped holding only the name, on the stated grounds that the name was the only
  thing about an account a person could change."* — false now; the account has a
  picture, a movable address and a place.
- *"**This one has no read.**"* — false now; the screen reads the city via
  `readHomeCity()`, and the docstring three paragraphs above says so.
- *"It renders an empty shell rather than `SettingsStates`. That component says
  'Couldn't load your settings.' — and nothing failed to load here; there was nothing to
  load. The other settings routes use it because *their* read can fail. This one has no
  read."* — **the conclusion (empty shell, not `SettingsStates`) is still right, and the
  reason it gives is now wrong.** The screen *does* have a read, and it can fail — but
  the failure is the city's, not the screen's, and the name above it is unaffected. So
  the correct reason is the one the code already implements and the docstring already
  gives *elsewhere*: a failed city read leaves the section absent rather than replacing
  the screen with an error.

**A docstring that argues for a design the code no longer has is worse than no
docstring: the next person believes it.** So the rewrite keeps the reasoning that
survives — the fallback rule, the publish-after-accept rule, the verbatim-API-message
rule, the house pattern of the four steps — and changes the conclusions that changed.

### The read question, answered explicitly

**The screen still reads nothing beyond the session *for the parts it owns*, and it has
one read that can fail — the city's.** The work item asks this to be answered rather
than assumed, so:

| What the screen shows | Where it comes from | Can it fail? |
|---|---|---|
| The name | `session.user.name` | **No** — the session carries it. A second `GET /api/auth/me` would answer the same question twice. |
| The picture | `session.user.avatar_url` | **No** — same read, same reason. |
| The address, and any pending change | `session.user.email`, `session.user.pending_email` | **No** — same read. |
| The city and its choices | `readHomeCity()` | **Yes** — two requests, either of which can fail. |

**So the answer is: the screen reads the city, and the failure is the city's.** It keeps
the empty shell rather than `SettingsStates`, because `SettingsStates`' *"Couldn't load
your settings."* would be false — the name, the picture and the address are all there
and all editable. The city section is simply absent. **This is what the code already
does, and what `/settings/account` already does with the same read and for the same
reason.** The docstring will say that, and it will say what the read *is*, so the next
reader is not left inferring it from a negative.

**The not-signed-in branch stays an empty shell, and its reason changes.** It renders
`{null}` — no city read at all, because there is no session to read the city with. The
branch's docstring currently says *"nothing failed to load here; there was nothing to
load"*; the honest reason is narrower: **there was no account to load anything about**,
and this visitor was redirected away by `homeRoute` in every case but one (the session
could not be read at all).

### The order, and why it reads as a profile

**The order is the account sheet's order: face, then name, then address.** The sheet
opens with the pair (disc and name together), the rail draws the disc beside the name in
that order too, and the screen that edits them presents them in the order they are
presented everywhere else.

**The place comes last, and it is a different kind of thing.** The picture, the name and
the address are *about the person*; the city is *where the digest comes from*. The
screen's own heading promises the order — *"Your picture, your name, your address, and
the city your Pulse Digest follows."* — and the order on the page is that order.

### The e2e, and the one rule it has to obey

**`frontend/e2e/profile-name.spec.ts` exists, and the rule is that the settings spec
must reach `/settings/profile` *by clicking*.** The existing spec reaches it two ways:
the account sheet's *"Edit your name"* link (a click) and `page.goto("/settings/profile")`
(a deep link, in four of its tests).

**A deep link is not a click, and a route tested only by deep link is a route whose
reachability is untested by construction** — the argument `settings-navigation.spec.ts`
makes about the whole settings surface. The new spec will reach the screen **through
the settings sub-nav**, which is the pattern that spec already uses:

```
await rail(page).getByRole("link", { name: "Settings" }).click();
await subnav(page).getByRole("link", { name: "Profile", exact: true }).click();
```

**And it will assert the rail's face and name move without a reload** — which is the
property the unit tests cannot see, because a unit test renders a page with a fixture
rather than a person who has just saved a picture.

### The axe gate, and where it goes

**The repo's pattern for axe is a Vitest/jsdom gate, not a Playwright one.**
`frontend/tests/*-a11y.test.tsx` — ten of them — each running `axe.run(document.body, …)`
with `color-contrast` disabled, and each auditing *every* state rather than the happy
one. **There is no `@axe-core/playwright` dependency and no e2e axe precedent.**

**So the axe gate goes where the other ten are: `frontend/tests/profile-a11y.test.tsx`.**
It audits the finished profile screen, in each of its states — the full screen, the
screen whose city read failed, and the screen with no picture and no name. **A screen
can be accessible when it is full and inaccessible when it is empty**, and each state is
a different document and a different set of rules.

**The e2e's axe run is not added here.** It would need the `axe-core` bundle injected
into the browser — a new mechanism, in a file whose job is to prove the *navigation* and
the *save*. **The jsdom gate is the house pattern and it covers the same surface.** If
the e2e axe run is wanted, it belongs in the item that adds an e2e axe harness.

## Technical Details

- **The rail's picture needs a locator that is not the name's.** The account row's
  accessible name is `Account: Maya Ahmed` — it carries the *name*, and the picture is
  `alt=""` and inside an `aria-hidden` wrapper, so it is not in the accessibility tree at
  all. **So the e2e asserts the picture through the DOM** — the `<img>`'s `src` inside
  the rail's disc — not through a role.
- **The email change sends real mail.** `POST /api/auth/profile/email` sends a
  confirmation link to the new address and a warning to the current one. The spec
  asserts the *pending UI appears* (the island sets the pending address locally, from
  the input, not from the server) and then **cancels the change** — the cancel is
  idempotent on the server, and leaving a pending change on the shared seed account would
  make the next run's screen show the pending block instead of the form.
- **The endpoint answers 202 identically for a free address and a taken one**, so the
  spec must not treat 202 as "available". It asserts the pending UI, not the verdict.
- **The picture's file must be a real image the server accepts.** The server identifies
  the format from the bytes, and `shared/constants.py` allows PNG, JPEG, WebP and GIF. A
  one-pixel PNG committed as a fixture is the honest way to do this — a file with the
  wrong bytes would be refused, and the refusal would be the test asserting the wrong
  thing.
- **The city control is a `<select aria-label="City">`.** The spec reaches it by that
  label. **It does not edit the zone** — the zone is paired with the delivery time on
  General, and `HomeCity` posts both back unchanged.
- **`homeRoute` ordering is unchanged**, and `redirect` is still called outside any
  try/catch. The rewrite touches prose, not control flow.

## The Gaps This Item Records Rather Than Hides

- **The e2e axe run is not here.** The repo has no e2e axe harness and no
  `@axe-core/playwright`; adding one is a separate piece of work. The jsdom gate is the
  house pattern and covers the same surface. **This is a gap, and it is recorded here
  rather than left for someone to discover.**
- **`Privacy` is missing from `settings-navigation.spec.ts`'s `SECTIONS` list.** It is
  in `SETTINGS_SECTIONS`, so the sub-nav offers it — but the e2e does not walk it. The
  spec's own docstring says the list *"must mirror `SETTINGS_SECTIONS` exactly"*, so this
  is a real gap in a spec that claims to be exhaustive. **The profile screen's
  acceptance criteria do not require it, but the spec's own rule does.** It is fixed
  here, because a spec that claims to mirror a list and does not is the exact failure
  this file exists to catch.
