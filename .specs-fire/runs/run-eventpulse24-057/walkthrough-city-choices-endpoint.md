# Implementation Walkthrough: The picker's choices endpoint

## Summary

`GET /api/public/cities` serves item 1's curated catalog as `{ value, label }` pairs —
165 cities, alphabetical, the same for everyone, **with no database query at all**.

The endpoint is small. What matters is which question it answers, because the bug this
whole intent exists to fix was a confusion between two questions that look alike:

| Question | Answered by | Changes when |
|---|---|---|
| "Which cities can the Pulse Preview show cards for **right now**?" | `/api/public/preview/cities` → `list_supported_cities()`, computed from `EventFit` | events are ingested or go stale |
| "Which cities may a reader **pick**?" | `/api/public/cities` → `domain.city_catalog` | code ships |

Treating the first as the second is what made the picker a mirror of the catalog: a reader
could only pick a city we had already collected, so a city nobody had picked was never
collected. `test_a_city_with_no_events_is_still_offered` is that fix in one assertion — the
preview can serve nothing at all, and Chittagong and Dhaka are both pickable.

`list_supported_cities()` is **unchanged**. It is still the right answer to its own
question. Its docstring now says which question that is, and which one it is not.

## Architecture

### A separate module, not another route in `preview_api.py`

The obvious shortcut was a second view next to `preview_cities`. It would have filed the
answer to the picker's question under the preview's name and prefix — re-creating, in the
code layout, the exact confusion the item was written to end. So: its own module, its own
router, mounted at `/public` alongside the preview's.

Two routers on one prefix is not novel here; `/settings` already carries five.

### It runs no query, and that is a test

The work item's technical note says the catalog is static, so the endpoint can be served
without touching the database — and explicitly warns against adding a read "to make it feel
symmetrical with the preview endpoint". A note is not a test, so:

```python
with django_assert_num_queries(0, using=CATALOG):
    with django_assert_num_queries(0, using=PERSONAL):
        get()
```

Verified it can fail: adding a `Source.objects.count()` to the view breaks exactly that
test.

The nearest precedent in the codebase is not the preview but
`ranking_transparency_api`, which projects `shared.constants` onto the wire and runs no
query either.

### Anonymous and cacheable are one fact

No `auth=`, no session, no `request.user`, no `personal` read. The response is
byte-identical for every caller — which is *why* it can be cached, not a separate nice
property. A response that depended on who asked could not be cached, and a shared cache
that ignored the session would hand one visitor's response to another.

Checked both ways, following the preview suite's own reasoning: **behaviourally**, by
comparing `response.content` for a signed-in and an anonymous request (bytes, not parsed
JSON — a cache sees bytes), and **structurally**, by `tests/architecture` reading the source
for `request.user` and `personal`, because a behavioural test passes against code that
reads the session and discards the value.

## Key Decisions

| Decision | Choice | Rationale |
|---|---|---|
| **Throttled?** | Yes, own scope `cities` | **Your checkpoint call.** Not because the response is expensive — serving it is cheaper than the Redis check that guards it — but because "every anonymous route on this surface is throttled" is an invariant someone can hold in their head, while "throttled unless it happens to be cheap" gets re-litigated per route. Its own scope, so neither route can spend the other's budget |
| **Cache TTL** | New `CITY_CHOICES_CACHE_CONTROL`: 1h browser, 1d edge, 1w stale-while-revalidate | **Your checkpoint call.** The preview's 60s/300s matches content that changes as events arrive; this answer changes when code ships. Accepted consequence: a deploy that adds a city may take up to a day to reach every edge — and a city a reader cannot find yet has the same remedy as one not yet added, which is `city-coverage-request` |
| **A separate module, not a route in `preview_api.py`** | Mine, from the item's stated purpose | Putting the picker's answer under the `/preview/` prefix would file it under the name of the question it is *not* answering |
| **Shared helpers extracted** | `public_surface.py` | Raised at code review. The first draft imported `_client_ip`, `_throttle_key`, `_cacheable` from `preview_api` — private names across modules. `apps/identity` keeps its own copy of `_client_ip`, but that is a different app; within one surface, a third hand-maintained copy of twenty lines of `TRUST_FORWARDED_FOR` logic is a third place to get it wrong, and the failure is silent |
| **`list_supported_cities` not renamed** | Docstring only | A rename would churn `digest_preferences`, `preview_api` and a published read interface for a clarity win the docstring delivers inside this diff |
| **Response is an object, not a bare array** | `{ "cities": [...] }` | Matches `PreviewCitiesOut`, and a top-level array cannot grow a sibling field — a catalog version or a count — without breaking every client |

## What the mutation check found

Two of the four code-review findings were faults in **my own tests**, and the suite going
green did not reveal either:

- `test_it_does_not_spend_the_previews_budget` exhausted the new route and checked
  `/preview/cities` — whose scope is `preview:cities`. A scope mistake would collide with
  `/preview`, scope `preview`. Changing the new route's scope to `preview` left all 17
  tests passing. Now parametrized over both preview routes, and the mutation is caught.
- `assert labels != sorted(labels)`, meant to prove a casefold sort rather than a byte
  sort, only ever worked by accident of the data. Removed, with the mechanism pinned where
  it can be — `choices()` sorting with `key=str.casefold`, in item 1's tests.

An architecture guard also turned out to be counting rather than checking: it asserted
there was exactly **one** router on `/public` before inspecting its `auth`. Adding a second
public router failed the guard instead of being covered by it. It now checks every router
on the prefix, so the new route is protected by a test nobody had to write for it.
