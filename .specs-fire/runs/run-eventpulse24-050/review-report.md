## The judgment this run rests on, stated plainly

**A third-party image now serves the project's object store in local development.**

That is a supply-chain decision, not a technical one, and it should be legible to whoever
reads this next:

- **What was verified:** the image runs genuine MinIO (`RELEASE.2026-08-04T00-00-00Z`,

- **What was not verified, and cannot be:** that the maintainer of `pgsty/*` will remain

- **Scope of exposure:** local development only. `BLOB_ENDPOINT` in production points at a

- **The reversal:** `dxflrs/garage` passes the same probe and is first-party. Switching is
  a compose + bootstrap change, not a backend change. It is named in `docker-compose.yml`
  so the option does not have to be rediscovered.

## What this run says about the one before it

Run 041 did the hard work correctly — the port, the adapters, the probes that changed the
design, the compose mitigation it measured rather than assumed. Its one wrong call was a
**diagnosis**, recorded as settled fact: *"it is access, not a tag typo. The user's
decision is to keep MinIO and `docker login`."*

The repository was **gone**, not forbidden. `hello-world` pulling fine was already in run
041's notes, and one more step — asking the registry whether the repository existed —
would have shown a 404. Instead the conclusion "it is access" was carried forward by four
subsequent runs, and five work items sat blocked behind a login nobody could have
performed.

**The lesson is about the error message, not the engineer.** Docker says *"pull access
denied … may require 'docker login'"* for a repository that is absent and for one that is
forbidden, and the two have opposite remedies. When a pull fails, ask the registry whether
the repository exists before reaching for credentials.
