## The actual diagnosis

"Hardcoded dates expired" is right but too vague to fix well. The precise mechanism:

**14 of the 17 fail with `not_found` — `"We couldn't find that event."`** The event is in the
database. The read path filters to events that have not started yet (`/api/catalog/events`
documents itself as *"Published, non-superseded events that have not started yet"*). The
fixtures place events at fixed datetimes — `START = datetime(2026, 11, 6, 3, 30, tzinfo=UTC)`
— which are now in the past, so the API correctly refuses to return them. The test asks a
future-only endpoint for a past event and gets a correct 404.

The remaining 3 are direct literal comparisons:

- `test_reminder_plan_api.py:467` — `assert [] == ['custom:90']`
- `test_reminder_plan_api.py:596` — `assert set() == {'1d', '1hr', '2d', '5d'}`
- `test_url_feed_read.py:306` — a `lastmod` that is now `now()` instead of the fixture's date

**And here is the part that decides the fix.** Three of the five files *already declare their
own `NOW`*:

```python
tests/delivery/test_reminder_plan_api.py:49      NOW = datetime(2026, 11, 10, 12, 0, tzinfo=UTC)
tests/e2e/test_timeline_and_conflict_proof.py:79 NOW = datetime(2026, 11,  4, 16, 0, tzinfo=UTC)
tests/ingestion/test_url_feed_read.py:42         NOW = datetime(2026, 11,  6, 12, 0, tzinfo=UTC)
```

and thread it into every **service** call that accepts it — `save_event(..., now=NOW)`,
`unsave_event(..., now=NOW)`, `last_seen_at=NOW`. The domain and service layers already have
the seam, and `domain/` has had it all along: `ranking.recency_band`, `ranking.why_this_tags`
and friends all take `now` as a parameter.

**The seam stops at HTTP.** When these tests go through the Django test client, the API view
calls `timezone.now()` internally, and nothing can tell it otherwise. So the test's declared
`NOW` governs the setup and the real wall clock governs the assertion. The two agreed in
early November and no longer do.

The tests already say when they are. Nothing was making the code listen.

## Approach

Add `freezegun` and freeze each affected module at **its own already-declared `NOW`**, so the
literals stay exactly as written and the production code finally reads the same clock the
fixtures do.

This is the structural fix the work item asks for, and it is explicitly *not* the thing the
work item forbids — no literal gets a later year, so nothing re-arms the same failure.

Per file:

1. **`test_reminder_plan_api.py`** — freeze at the existing `NOW` (2026-11-10 12:00 UTC).
   `AFTERNOON_START` and `LATE_START` are 2 and 4 days after it, which is what the comments
   describe ("2026-11-11 18:00 in LA", "2026-11-13 23:30 in LA"). Both become future again.
2. **`test_timeline_and_conflict_proof.py`** — freeze at the existing `NOW` (2026-11-04
   16:00 UTC); `START_UTC` is 11 hours later and becomes future again.
3. **`test_url_feed_read.py`** — freeze at the existing `NOW` (2026-11-06 12:00 UTC).
4. **`test_save_race.py`** and **`test_personal_events_and_saved_catalog.py`** — these declare
   only `START` (2026-11-06 03:30 UTC) and no `NOW`. Introduce `NOW = START - timedelta(days=1)`
   and freeze there, so the single existing literal still anchors the file.

**`tick=True` on every freeze.** A hard-frozen clock would make UUIDv7 primary keys share a
timestamp prefix, and several of these tests assert ordering — `test_a_save_is_idempotent_and_one_row`
and the pair-ordering assertions in the timeline proof. `tick=True` starts at the stated
instant and lets time advance normally from there, which keeps UUID7 monotonic while still
putting the fixtures in the future. The failure mode of getting this wrong is a flaky
ordering test, which is worse than the bug being fixed.

## Technical Details

**Why not relative dates.** The obvious alternative is `START = timezone.now() + timedelta(days=3)`.
Rejected: it makes the suite's behaviour depend on when it runs. These files assert on local
wall-clock times in named timezones — `test_reminder_plan_api.py`'s comments spell out
"2026-11-11 18:00 in LA" — so a run that crosses midnight, a DST boundary, or a weekday
boundary would produce different expected values than a run that does not. That is how a
suite becomes intermittently red for reasons nobody can reproduce, which is the same disease
as the current bug wearing better clothes.

**Why freezegun over a hand-rolled clock port.** A clock port would mean threading a `now`
parameter through the HTTP layer — changing production signatures across five apps so the
tests can speak. The service layer already has that seam and it was the right call there. At
the view layer the same move would add a parameter that production never varies, which is
test-shaped code in production. Freezing the clock is the smaller change and leaves the
production API honest.

**Risk, stated up front:** `freezegun` patches `datetime` globally for the duration. Three
things in this codebase could interact badly and will be checked, not assumed:

1. **UUIDv7 ordering** — addressed by `tick=True`, verified by running the ordering assertions.
2. **Celery eager tasks** inside e2e tests — these run in-process, so they inherit the frozen
   clock. That is what we want, but it is worth confirming no task compares a frozen `now`
   against a real-clock timestamp written earlier.
3. **`psycopg` / Postgres `now()`** — the database's clock is *not* frozen. Any assertion
   comparing a Python-side frozen timestamp with a DB-generated `DEFAULT now()` column would
   now mismatch by the offset. If this bites, the fix is to pin that column in the fixture
   rather than to abandon the approach — and I will say so rather than quietly widening an
   assertion to make it pass.

If any of these three turns out to block the approach, I will stop and report rather than
force it through.

**Ruff `DTZ` is enabled** (`select = [..., "DTZ", ...]`), which bans naive datetimes. Every
frozen instant is already tz-aware, so this should be a non-issue — confirmed by lint, not by
assumption.

**Out of scope, flagged not folded in:** the suite takes **628 seconds**. `pytest-xdist` is
not installed; adding it and running `-n auto` would likely cut that several-fold. It is not
in this work item's acceptance criteria, so it is not in this plan. Worth its own decision.
