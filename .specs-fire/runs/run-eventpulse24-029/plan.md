## The actual diagnosis

"Hardcoded dates expired" is right but too vague to fix well. The precise mechanism:

**14 of the 17 fail with `not_found` — `"We couldn't find that event."`** The event is in the
database. The read path filters to events that have not started yet (`/api/catalog/events`
documents itself as *"Published, non-superseded events that have not started yet"*). The
fixtures place events at fixed datetimes — `START = datetime(2026, 11, 6, 3, 30, tzinfo=UTC)`
— which are now in the past, so the API correctly refuses to return them. The test asks a
future-only endpoint for a past event and gets a correct 404.

The remaining 3 are direct literal comparisons:

- `test_reminder_plan_api.py:467` — `assert [] == ['custom:90']`
- `test_reminder_plan_api.py:596` — `assert set() == {'1d', '1hr', '2d', '5d'}`
- `test_url_feed_read.py:306` — a `lastmod` that is now `now()` instead of the fixture's date

**And here is the part that decides the fix.** Three of the five files *already declare their
own `NOW`*:

```python
tests/delivery/test_reminder_plan_api.py:49      NOW = datetime(2026, 11, 10, 12, 0, tzinfo=UTC)
tests/e2e/test_timeline_and_conflict_proof.py:79 NOW = datetime(2026, 11,  4, 16, 0, tzinfo=UTC)
tests/ingestion/test_url_feed_read.py:42         NOW = datetime(2026, 11,  6, 12, 0, tzinfo=UTC)
```

and thread it into every **service** call that accepts it — `save_event(..., now=NOW)`,
`unsave_event(..., now=NOW)`, `last_seen_at=NOW`. The domain and service layers already have
the seam, and `domain/` has had it all along: `ranking.recency_band`, `ranking.why_this_tags`
and friends all take `now` as a parameter.

**The seam stops at HTTP.** When these tests go through the Django test client, the API view
calls `timezone.now()` internally, and nothing can tell it otherwise. So the test's declared
`NOW` governs the setup and the real wall clock governs the assertion. The two agreed in
early November and no longer do.

The tests already say when they are. Nothing was making the code listen.

## Approach

Add `freezegun` and freeze each affected module at **its own already-declared `NOW`**, so the
literals stay exactly as written and the production code finally reads the same clock the
fixtures do.

This is the structural fix the work item asks for, and it is explicitly *not* the thing the
work item forbids — no literal gets a later year, so nothing re-arms the same failure.

Per file:

1. **`test_reminder_plan_api.py`** — freeze at the existing `NOW` (2026-11-10 12:00 UTC).
   `AFTERNOON_START` and `LATE_START` are 2 and 4 days after it, which is what the comments
   describe ("2026-11-11 18:00 in LA", "2026-11-13 23:30 in LA"). Both become future again.
2. **`test_timeline_and_conflict_proof.py`** — freeze at the existing `NOW` (2026-11-04
   16:00 UTC); `START_UTC` is 11 hours later and becomes future again.
3. **`test_url_feed_read.py`** — freeze at the existing `NOW` (2026-11-06 12:00 UTC).
4. **`test_save_race.py`** and **`test_personal_events_and_saved_catalog.py`** — these declare
   only `START` (2026-11-06 03:30 UTC) and no `NOW`. Introduce `NOW = START - timedelta(days=1)`
   and freeze there, so the single existing literal still anchors the file.

**`tick=True` on every freeze.** A hard-frozen clock would make UUIDv7 primary keys share a
timestamp prefix, and several of these tests assert ordering — `test_a_save_is_idempotent_and_one_row`
and the pair-ordering assertions in the timeline proof. `tick=True` starts at the stated
instant and lets time advance normally from there, which keeps UUID7 monotonic while still
putting the fixtures in the future. The failure mode of getting this wrong is a flaky
ordering test, which is worse than the bug being fixed.

## Technical Details

**Why not relative dates.** The obvious alternative is `START = timezone.now() + timedelta(days=3)`.
Rejected: it makes the suite's behaviour depend on when it runs. These files assert on local
wall-clock times in named timezones — `test_reminder_plan_api.py`'s comments spell out
"2026-11-11 18:00 in LA" — so a run that crosses midnight, a DST boundary, or a weekday
boundary would produce different expected values than a run that does not. That is how a
suite becomes intermittently red for reasons nobody can reproduce, which is the same disease
as the current bug wearing better clothes.

**Why freezegun over a hand-rolled clock port.** A clock port would mean threading a `now`
parameter through the HTTP layer — changing production signatures across five apps so the
tests can speak. The service layer already has that seam and it was the right call there. At
the view layer the same move would add a parameter that production never varies, which is
test-shaped code in production. Freezing the clock is the smaller change and leaves the
production API honest.

**Risk, stated up front:** `freezegun` patches `datetime` globally for the duration. Three
things in this codebase could interact badly and will be checked, not assumed:

1. **UUIDv7 ordering** — addressed by `tick=True`, verified by running the ordering assertions.
2. **Celery eager tasks** inside e2e tests — these run in-process, so they inherit the frozen
   clock. That is what we want, but it is worth confirming no task compares a frozen `now`
   against a real-clock timestamp written earlier.
3. **`psycopg` / Postgres `now()`** — the database's clock is *not* frozen. Any assertion
   comparing a Python-side frozen timestamp with a DB-generated `DEFAULT now()` column would
   now mismatch by the offset. If this bites, the fix is to pin that column in the fixture
   rather than to abandon the approach — and I will say so rather than quietly widening an
   assertion to make it pass.

If any of these three turns out to block the approach, I will stop and report rather than
force it through.

**Ruff `DTZ` is enabled** (`select = [..., "DTZ", ...]`), which bans naive datetimes. Every
frozen instant is already tz-aware, so this should be a non-issue — confirmed by lint, not by
assumption.

**Out of scope, flagged not folded in:** the suite takes **628 seconds**. `pytest-xdist` is
not installed; adding it and running `-n auto` would likely cut that several-fold. It is not
in this work item's acceptance criteria, so it is not in this plan. Worth its own decision.

### Deviations from the approved design — needing approval

One, and it replaces an answer given at checkpoint 1.

| # | Approved at checkpoint 1 | Proposed instead | Why |
|---|---|---|---|
| 1 | `total` comes from **one `COUNT(*)` per request**, same filters as the candidate query | `total` is the **size of the ranked pool**, with no `COUNT(*)` at all | A `COUNT(*)` would be **wrong**, not just redundant — see below |

**Why the approved answer cannot be implemented honestly.** `list_public_candidates` applies
FR-14's staleness bound **in Python**, after the SQL has narrowed the set, because the bound is
per-source and the database "cannot compare a column against another column times a
multiplier":

```python
for event in queryset.order_by("start_time_utc", "id")[: limit * CANDIDATE_OVERFETCH_FACTOR]:
    age = now - event.last_seen_at
    stale_after = timedelta(hours=source.freshness_ttl_hours) * DIGEST_STALE_TTL_MULTIPLIER
    if age > stale_after:
        continue
```

A `COUNT(*)` with "the same filters" can only apply the SQL-expressible ones. It would count
events that the Python filter then drops — so the section head would advertise *"147 events ·
scroll for more"* and the user would page to the end and find 120. A number that cannot be
reached is worse than no number.

The pool size is the honest count: it is exactly what the user can page to. It also costs
nothing extra, because the pool is already in memory.

**The bound, stated rather than buried.** `MAX_CANDIDATE_POOL_SIZE = 200`. Browse fetches one
pool at that cap, ranks it, and pages within it. The design's own mockup shows 147 events in a
week, so 200 has room — but a city with more than 200 eligible events in its 7-day window will
report 200 and page to 200. **That is a real limit and it should be written in the service's
docstring**, not discovered later. If it ever binds, the fix is a decision about what Browse
is for, not a bigger constant.

**This also settles D5 (paging).** SQL-level `OFFSET` on top of a Python-filtered over-fetch is
unsound: page 2 could re-run the fetch, drop different stale rows, and show an event already
seen on page 1 or skip one entirely. Paging **within one ranked pool** is sound by
construction — one list, one order, sliced. The total order `(score desc, start_time asc, id
asc)` still applies, and it is what makes the slice stable.

### Approach

A single bounded pool, ranked once, sliced per request.

1. **Resolve the user's context** — city and timezone from `digest_preferences`. No city →
   the designed empty state (checkpoint 1, Risk 5), not an error and not a geo-IP guess.
2. **Fetch the pool** — `list_public_candidates(now=…, city=…, starts_before=…, limit=200)`.
3. **Rank** — `domain.ranking.relevance_score` per candidate; `why_this_tags` for the card's
   tag row; `domain.confidence` for the confidence row. The **Relevance Pulse**, never the
   Event Fit (AD-10).
4. **Join the personal side** — one `IN` query for this user's `SavedEvent` rows over the pool's
   ids → `is_saved` per card (D6).
5. **Gate** — quota state via `save_cap` + `entitlement.is_pro` (D8).
6. **Split and slice** — tier 1 is the top 3, tier 2 the rest (D7, server-named); slice by
   `offset`/`limit`; cap the must-know stripe at one per response.

### Technical Details

**The wall (AD-3).** Two reads, two aliases, joined in Python. No transaction spans them and no
query joins them — the pattern `digest_candidates.py` already documents.

**The contract that will catch a mistake (AD-10).** `browse_read.py` lives in
`apps.personalization` and may import `apps.ingestion.services.catalog_read` but **not**
`apps.ingestion.event_fit.*`. `make lint-imports` is in this item's gate; a breach fails the
build rather than shipping a stranger's explanation on a personal surface.

**`starts_before` is additive.** Default `None` means no upper bound, which is today's
behaviour. The digest never passes it.

**Ranking cost, to be measured not assumed** (design Risk 3). 200 candidates scored in Python
per request. The Digest already does this for a 60-pool once per user per day; Browse does it
per page view. The plan is to measure it with `CaptureQueriesContext` and a timing assertion
on the service, and **report the number**. If it is bad, the answer is a smaller pool, not
moving the score into SQL — the score is domain logic and `domain/` is where it is allowed to
live.

**`now` must be timezone-aware.** Every read here takes an aware instant; the window arithmetic
is done in the user's zone and converted, because "tonight + 7 days" is a local idea.

**The decision, and it is the item's real substance.**

**No new tokens.** The acceptance criterion says *"No new colour tokens, CSS variables or
spacing tokens are introduced"* — and `styles/tokens.css` resets `--breakpoint-*`,
`--spacing:*` and the type scale wholesale, so anything not declared **generates no CSS
at all**: `p-[22px]` would silently produce a card with no padding, exactly the failure
`tests/spacing-scale.test.ts` was written to catch. `gap-5` (20px) and `px-6` (24px) are
the nearest on-scale steps.

So every off-scale number is written as a **bracketed exact value**, which is the
codebase's own established idiom for "a size the scale does not have" — `size-[6px]`,
`min-h-[44px]`, `max-w-[260px]` already appear across `components/`. `tests/spacing-scale.test.ts`
explicitly leaves bracketed values alone. That is how 22px padding, the 20px grid gap,
the 600px lede width and the 800px h1 width get expressed, with **zero new tokens**.

**For the type scale, the two missing slots are mapped to the nearest existing tokens:**

- **h1 → `--type-scale-display-lg`** (48px source-serif 700). It is the design's own
  `display.xl` floor (48-64px) and the largest display token that exists. The mockup's
  56px would need a new token, so 48px it is. **Recorded as a deviation.**
- **Section head → `--type-scale-headline-lg`** (28px source-serif 600). The design says
  26px `display.sm`; the closest existing 600-weight display-family token is
  `headline-lg` at 28px. **Recorded as a deviation.**

**For the grid, the 1280px breakpoint is the one thing I will not fake.** There is no
`xl` breakpoint and no way to add one without introducing a CSS variable — which the AC
forbids. The grid uses the codebase's existing three-step idiom, which is what every
other grid in `components/` uses:

```
grid-cols-1  md:grid-cols-2  lg:grid-cols-3
```

`lg` is 1024px, so the 3-column grid appears at 1024px rather than the design's 1280px.
**The consequence is stated, not hidden:** at 1024-1279px the inner width after the
240px sidenav and the shell's padding is ~760px, so a 3-column grid gives ~240px cards
against the design's ~279px. The cards are legible at 240px (the digest's cards are
narrower than that at the same `lg` breakpoint and ship), but the mockup's exact card
width is not reproduced. **A custom `xl` breakpoint would fix this and is exactly the
"new CSS variable" the AC forbids.** Recorded as a deviation with its reasoning.

### Architecture: server component, one read, no client fetch

The whole route is a **server component**, like `/timeline` and `/`:

1. `getSession()` → `homeRoute(session)` decides the redirect (anonymous → `/preview`,
   half-onboarded → `/onboarding`).
2. `readBrowse()` → the **one** backend read, `GET /api/personal/browse`, with the
   visitor's cookies forwarded (`sessionHeaders()`), exactly as `lib/timeline-read.ts`
   does.
3. The page renders the payload. **It re-ranks nothing, re-sorts nothing, and re-decides
   nothing** (AD-10). `tier_2_starts_at` is the server's, so the section split is the
   server's.

**The "More events below" chunk is the one client-side thing, and it is bounded.** The
soft cap is 24 cards; the server's `offset`/`limit` pages within one ranked pool. So the
anchor is a **client component** (`"use client"`) that fetches the next chunk and
appends it — with the ordering and the tier split still the server's, because the
chunk arrives already ordered.

**Why the client component is not a violation of AD-10.** AD-10 forbids *re-deciding* a
persisted fact. The client does not rank, sort, tier or re-bucket; it appends cards the
server sent in the server's order, and the server's `tier_2_starts_at` says where the
second section begins. The alternative — a server round-trip per page — would make every
scroll a full page reload, which is what "no pagination chrome, no page numbers" is
trying to avoid.

**One honest limitation, stated in the plan rather than discovered later.** The fake
throttle does not persist between requests in `ADAPTER_MODE=fake` (Finding 23 in the
previous item's review). The quota note therefore reads `0 of 1 save used` after a save,

### Technical Details

**The 24-card soft cap and `has_more`.** The server's `BROWSE_PAGE_SIZE` is 24 and
`has_more` is `offset + len(cards) < total`. The page renders at most 24 cards and the
anchor appears only when `has_more` is true. The "More events below" anchor is a
**`Text.Meta` anchor, not a button** — the criterion forbids pagination chrome and a
"Load more" button.

**The section split.** `tier_2_starts_at` is an index into the *pool*, and the first page
carries the top 3 at tier 1 and the rest at tier 2. The grid renders section 1's head,
section 1's cards, section 2's head, section 2's cards — one `<ul>` per section, so
each section is a real list. **A `<ul>` per section, not one `<ul>` with heads inside
it**: a list whose children are headings and `<li>`s is not a list, and the `list` axe
rule is *serious* — the city page's own a11y test has a mutation probe for exactly that.

**The confidence indicator is the Relevance Pulse, and it says so.** Browse is an authed
surface whose section head says *"3 worth your attention today"* — so its cards carry the
**personal** explanation, and the indicator is labelled "Relevance", exactly as
`PulseCard` does. **The Event Fit is forbidden here** (AD-10), and the import contract
that guards it lives in the backend; on the frontend the same rule holds because the
Browse card renders `card.confidence` (a server-stated bucket) and never computes a
score.

**The quota note's reset time.** The API sends `resets_in_seconds`, not a clock time.
The note reads *"resets {time}"*, so the frontend has to render a time from a duration.
**The rule: the note states the duration in hours, not a wall-clock time.** "resets in
8h" is what the data supports; "resets 8:00 AM" (the mockup's copy) is a wall-clock
claim the payload does not carry. The mockup's own number is from a persona, not from an
API. **Recorded as a deviation from the mockup, in favour of the payload** — the same
rule the city page followed when it worded its count to the payload rather than to the
mockup.

**The eyebrow's terracotta dot.** The design says "terracotta 6×6 dot glyph + the text in
`{color.ink.muted}`". So the *text* is muted and the *dot* is terracotta — the reverse
of the built `city-page.tsx`, whose eyebrow puts the whole line in terracotta. This is
the Browse design's own wording and it is followed: a `size-[6px] rounded-full
bg-accent-terracotta` span, then the text in `text-ink-muted`.

**The card's kicker.** The design puts the stripe's meaning in words as well as colour
(WCAG 1.4.1): `public` → "Public", `must_know` → "Must-know". **Two labels, two
colours, no third.** The mockup's kicker reads "Public · 8:00 PM · Free" — the time and
the price. The payload carries the time but **no price**, so "Free" is not said: the
backend sends no price field, and inventing one is a fact the frontend does not have.

**Motion.** The only animation in the product is `.skeleton-pulse` (1800ms) and the only
transition is `.fade-in`. `tests/architecture.test.ts` scans every `.tsx` for
`transition-*`/`duration-*`/`delay-*`/`ease-*`/`animate-*` classes, so the card's hover
uses a **colour swap with no transition class**, exactly as `PulseCard` does.

**The card links to the detail screen.** `/events/{event_id}` — the same target
`PulseCard` uses, because a Browse card is the same noun as a Digest card and the
detail route is the only one that exists for a signed-in user's event.

**No client-side re-ranking.** The page renders `cards` in the order the server sent
them. A test asserts the rendered order equals the payload's order.

## Work Item: frontend-browse-search

**Mode:** `confirm` — checkpoint 1 (plan). This is checkpoint 1 of 1.
**Design source:** `DESIGN.md` §`component.input.search.browse` (Amendment A-11) and
`EXPERIENCE.md` §`Component.Surface.Browse` → "Inline keyword search". Visual references:
`mockups/browse-desktop-filtered.html` (the filtered state) and

### The finding that shapes this plan: the design's ten tags do not exist on the server

The work item's acceptance criteria include, verbatim:

> - `tag:<token>` literals match **only** against the why-tag set, and combine with plain
>   words by AND
> - The ten documented tags all work: music, tech, community, arts, family, food, sports,
>   outdoor, indoor, rooftop
> - An unknown `tag:` token matches nothing rather than falling back to a plain-word match
>   — silently widening a constrained query would make the grammar untrustworthy

**These three cannot all be satisfied against the real payload.** The design's ten tokens are
not why-tag keys. The server's vocabulary is:

| Source | Keys |
|---|---|
| `RANKING_TAG_ORDER` (`backend/shared/constants.py:994`) | `discovery`, `nearby`, `tonight`, `tomorrow`, `weekend`, `saved` |
| Chip-match tags (`domain/ranking.py:why_this_tags`) | `matches_<chip_key>` for ten *other* slugs |

and the ten chip slugs (`INTEREST_CHIPS`, `constants.py:565`) are `tech_meetups`,
`sports_fitness`, `arts_culture`, `family_kids`, `community_volunteering`,
`outdoors_nature`, `classes_workshops`, `markets_fairs`, `talks_lectures`,
`government_civic`.

So, mapped honestly:

| Design token | Server counterpart | Status |
|---|---|---|
| `tag:tech` | `matches_tech_meetups` | mapped |
| `tag:arts` | `matches_arts_culture` | mapped |
| `tag:family` | `matches_family_kids` | mapped |
| `tag:community` | `matches_community_volunteering` | mapped |
| `tag:sports` | `matches_sports_fitness` | mapped |
| `tag:outdoor` | `matches_outdoors_nature` | mapped |
| `tag:music` | — | **no counterpart at all** |
| `tag:food` | — | **no counterpart at all** |
| `tag:indoor` | — | **no counterpart at all** |
| `tag:rooftop` | — | **no counterpart at all** |

`DESIGN.md` itself says the tag vocabulary *"matches the why-tag tokens rendered on each
card"* — but the tokens rendered on each card are `tagLabel(tag)` of the **server** keys
(`frontend/lib/digest-labels.ts`), which is "Arts & culture", "Outdoors & nature", "Tonight",
"Nearby" — never "music" or "rooftop". **The design's sentence describes a vocabulary the
design did not check against the payload.**

**The decision: an explicit client-side alias table, with the four unmapped tokens
documented as unmapped.**

1. **The six mappable tokens resolve to their real server keys.** `tag:arts` matches
   `matches_arts_culture`; `tag:tech` matches `matches_tech_meetups`; and so on. The
   alias table is data, not logic, and it lives beside the label table in
   `lib/digest-labels.ts` — the same file that already carries the frontend's translation of
   the server's tag vocabulary, and the same file whose drift is already guarded by a test
   that reads `backend/shared/constants.py`.

2. **The four unmappable tokens (`music`, `food`, `indoor`, `rooftop`) match nothing.**
   This is the AC's own rule — *"an unknown `tag:` token matches nothing rather than
   falling back to a plain-word match"* — applied honestly rather than worked around. They
   are *not* aliases for a chip, because no chip means "music" and no chip means "rooftop";
   and they are *not* matched against the card's text, because that would be exactly the
   "silently widening a constrained query" the AC forbids.

3. **The `tag:` vocabulary the input advertises is the one that actually works.** The
   placeholder is fixed by the AC and stays verbatim —
   `Search this week — jazz, free, outdoor, tag:music` — and `tag:music` is a real
   *plain word* example that also happens to be a design-era tag. **This is a real
   inconsistency in the spec, and it is recorded rather than silently repaired**: the
   placeholder's `tag:music` matches nothing on the real payload. The hint line below the
   input — the place the design puts the tag vocabulary — lists the vocabulary that works.

4. **The backend is not changed.** The why-tag set is a persisted, server-stated fact
   (AD-10), and the chip keys are *"stable forever even if the label changes"*
   (`constants.py`). A search alias is a **frontend translation of a server fact**, which is
   exactly the seam `digest-labels.ts` documents: *"The server states the fact; the client
   speaks the user's language."* Changing the backend to mint `music`/`rooftop` tags would
   mean inventing why-tags that mean nothing in the ranking, and would put a search
   vocabulary into the relevance explanation, where it does not belong.

**Consequence for the AC "the ten documented tags all work":** six of the ten work as
documented; four are documented as not matching, because the server has no such fact to
match. This is a **deviation**, listed below, and it is the honest reading of the item's own
"unknown tags match nothing" rule. The alternative — making all ten work by aliasing
`music` onto `matches_arts_culture` — would put the word "music" on a card tagged "Sports &
fitness", which is a lie about the card.

### The second finding: the search must own both grids, and they live in two components

`BrowseGrid` is a server component (the payload arrives from `readBrowse`) and `BrowseMore`
is a client island that appends the next chunk. **A query typed into a client island cannot
filter a server-rendered grid.** So the search needs a single client boundary that owns
**both** the initial cards and the appended chunk.

**The approach: one client island that owns the whole filterable surface.**

- `components/browse/browse-search.tsx` — `"use client"`. It owns the query state, the
  input, the count line, the two empty states, **and** the rendering of both the initial
  cards and the appended chunk.
- `BrowseGrid` and `BrowseMore` become **presentational** — they take the already-filtered
  card list and render it. The tier split stays the server's (`tier_2_starts_at`), and the
  appending stays the client's own chunk fetch.

**Why not a server-side search?** The AC says *"Filtering is instant on the loaded set, with
no network request per keystroke"* and *"matching runs client-side over the loaded set,
decided at capture"*. A server search would be one network round trip per keystroke — the
exact thing the AC forbids.

**Why not keep `BrowseGrid` server-rendered and filter it in place?** It cannot be: a
server component's output is fixed at request time. The grid must become a client island for
the filter to reach it. This is a real structural change and is listed as a deviation.

**The cost, stated plainly:** the initial cards are now serialised into the client bundle as
props rather than rendered on the server. For 24 cards that is a payload the server
component would have rendered to HTML instead. **This is the price of the AC's
"no network request per keystroke", and it is the AC's own trade, not a preference.**

**The chunk-bounded limitation.** The search sees only the *loaded* cards — the first page
plus whatever the reader has pulled in. A match that sits past the current chunk does not
appear until that chunk loads. This is stated in the component's own doc comment (the AC
requires it there), shown to the reader in the count line's *"of N events total"* clause,
and never papered over.

### The two empty states, distinguishable in the DOM

The AC is explicit: *"The two empty states are distinguishable in the DOM, not just to the
eye"* — a test asserts that the no-match state and the zero-events state render different
copy **and different recovery actions**.

| | Zero-events | No-match |
|---|---|---|
| Component | `BrowseEmpty` (existing, `browse-states.tsx`) | `BrowseSearchEmpty` (new, `browse-search.tsx`) |
| Heading | "Nothing nearby tonight. Try a wider city?" | "Nothing matched." |
| Body | "There is nothing on in your city across tonight and the next seven days…" | "No cards in tonight + 7 days satisfy both *quantum* and *poetry*. Drop a term, or browse the full list." |
| Recovery | **"Change city"** → `/settings/account` | **"Clear filters"** → empties the input |
| Test hook | `data-browse-empty` | `data-browse-search-empty` |

**They are different answers to different questions** — "your city has nothing on" versus
"your query found nothing in what is loaded" — and the recovery actions point at different
places. A reader who sees "Nothing matched." must not be offered "Change city": their city
is fine.

### The grammar, decided in code

`lib/browse-search.ts` (new, pure, no React) owns the tokenisation and the matching, so it
can be tested directly without rendering:

```
tokenize("  Jazz   FREE  ")
  → { words: ["jazz", "free"], tags: [] }

tokenize("jazz tag:music")
  → { words: ["jazz"], tags: ["music"] }

tokenize("tag:")           → { words: [], tags: [] }   // a tag with no token is not a tag
tokenize("tag:unknownxyz") → { words: [], tags: ["unknownxyz"] }  // and it matches nothing
```

- **Plain words**: whitespace-split, lowercased, trimmed. AND-matched against the card's
  **headline**, its **where line** (venue name, then venue city) and its **why-tag tokens**.
- **`tag:<token>`**: matched **only** against the card's why-tag tokens (the raw server
  keys, after alias resolution). AND with the plain words.
- **A plain word that is also a tag name** (`music`) is a plain word — `tag:` is the only
  way to constrain, which is what makes the grammar learnable.
- **A card matches only if *every* term matches something.**
- **An unknown `tag:` token matches nothing** — it is not dropped, not treated as a plain
  word, and it makes the whole query match nothing. Silently widening a constrained query
  is the failure the AC names.

**A term matches a tag** if the tag set contains it *or* an alias resolving to it. The
matching is against the **raw server keys** (`card.tags`), not the rendered labels — the
rendered label "Arts & culture" is a translation, and matching on translations would make
the grammar depend on copy changes.

count is announced rather than the grid silently changing under the reader.

# Work Item: `frontend-browse-save-button`

**The Inline Save Button — State Machine, Quota Wall and the Two Refusals**

Mode `confirm` — one checkpoint, this plan. 13 acceptance criteria.

## The shape of the thing

`Component.Button.Save.Inline` — the one element Browse cards add to the digest card
anatomy. The card body is not a button; Save is.

**The backend is already correct and already distinguishes the two refusals.** This is
the good news of the item: there is no new endpoint to build, no new error to define and
no backend change to make. `POST /api/personal/saved-events/{catalog_event_id}` already
answers 409 twice, and the two are told apart by `code`:

| Refusal | `code` | `details` | What happened |
|---|---|---|---|
| The clash | `scheduling_conflict` | `{event_id, conflicts[]}` | **The save row was written, and the pair is active.** The event *is* saved; there is a choice waiting. |
| The cap | `save_cap_reached` | `{cap, upgrade_hint}` | **The save did not happen.** The gate refused before any row existed. |

**That difference is the whole design of the item**, and it decides what each refusal says.
A `scheduling_conflict` is not a failed save — saying "Couldn't save that" would be false,
and the button going back to "Save" would invite the reader to press it again and get the
same 409. A `save_cap_reached` is not a save at all — the row does not exist, and the
allowance does not come back.

**The refusal is calm, and the item says so twice.** `save_cap.py`: *"A cap that interrupts
with a modal is a cap that trains people to dismiss prompts."* Both refusals render as an
inline line under the button, in the normal flow, with no overlay, no portal and no
toast. The criterion that forbids the modal is *asserted by a test*, because a test that
only checked the copy would not notice a modal appearing later.

## The decision this plan had to make first

**The Save button is a client island, and `browse-card.tsx` stays a server component.**

`browse-card.tsx:186` already reserves the slot:

```tsx
<div className="relative z-10 flex items-start justify-end" data-browse-save-slot />
```

The slot was left empty by the grid work item with the comment *"The Save affordance is
its own work item"* — and it is empty because a Save button that talks to the API cannot
be a server component. It holds state (idle → saving → saved), it fires a request, and it
answers a 409.

So: a new `components/browse/browse-save.tsx`, `"use client"`, mounted **inside** the
card's existing slot. The card renders it and passes the payload's facts down:

| Prop | From | Why |
|---|---|---|
| `eventId` | `card.event_id` | The **catalog** id — the path parameter the endpoint takes. The card also carries `slug`, and the slug is the public page's address, not this one's. |
| `eventName` | `card.title` | The `aria-label`'s "{event name}". |
| `saved` | `card.is_saved` | The **initial state**, so an already-saved event renders "Saved ✓" on first paint rather than flashing "Save" (criterion 13). |
| `quota` | the payload's `quota` | The wall (criterion 8) and the Pro exemption (criterion 9). |
| `slug` | `card.slug` | The "Open" link's target on a conflict refusal. |

**The quota arrives with the payload and is read, not re-derived.** `BrowseOut.quota` is
`BrowseQuotaOut` — `{used, cap, resets_in_seconds, is_pro}`, with `cap: null` for a Pro
account. The rule the server states is the rule the client uses:

```
Pro            → cap === null (or is_pro) → never the quota state, never the muted label
Free, spent    → cap !== null && used >= cap → "1 of 1 used today", disabled
Free, not spent → the ordinary "Save" button
```

**The page renders the payload and decides nothing** — but the quota is not a decision,
it is a fact the payload carries. The gate is still `check_save_allowed` on the server;
the client never refuses a save on the strength of a string it rendered. That is exactly
the rule `lib/browse-labels.ts`'s `quotaNote()` already documents: *"the API reports the
allowance without spending it: it is a sign above the gate, not the gate."*

**A Pro user never sees the quota state.** The check is `cap === null || is_pro` — and
`quotaNote()` already treats a missing `cap` as a null one, because Django Ninja omits
the field when it is null. **Two sources of truth would be a bug**, so the island reads
the *same* shape `quotaNote()` reads.

**Criterion 9 asks for a test that would fail if the entitlement check were dropped.**
That test is the whole point of criterion 9: it renders a Pro quota (`cap: null,
is_pro: true`), presses save twice, and asserts two requests went out and the button
never rendered "1 of 1 used today". Drop the `cap === null` check and the test fails —
which is what makes it worth writing.

## The state machine

```
idle ──press──▶ saving ──2xx──▶ saved ──press──▶ idle (un-save)
                  │                 │
                  │                 └── 1500ms lockout, then press again
                  ├──409 cap──▶ idle + inline cap line
                  └──409 clash──▶ saved + inline conflict line
```

**The labels.** "Save" in the ordinary ink; "Saving…" in `ink-muted`; "Saved ✓" in
`color.signal.success` (`--color-signal-success`, which `tokens.css` declares twice —
once per theme — and which the codebase already uses as `bg-signal-success`).

**The 1500ms lockout (criterion 2).** The `saved` state persists for at least 1500ms
before another interaction is accepted, so a fast double-tap cannot flicker the label.
This is a real state, not a CSS trick: the button is `disabled` while the lockout runs,
and the lockout is cleared by a timer. The criterion says *"persists at least 1500ms"* —
the implementation holds for exactly 1500ms and the test asserts the label is still
"Saved ✓" just before it expires.

**The morph is the confirmation (criterion 3).** From `saved`, a second tap un-saves.
**There is no confirmation dialog**, and there is no undo toast — the label change *is*
the feedback. A destructive confirmation on an un-save would be the product's whole
posture inverted: the thing being removed is a thing the user put there themselves, and
the save it would delete is recoverable by pressing the button again.

**`Esc` cancels an in-flight save — scoped to the label, and this is the honest version.**
The technical note asks the right question: *"check whether that rollback actually exists
before claiming the cancel works."* I checked, and the answer is **no**:

- `save_event()` (`apps/personalization/services/saved_events.py:106`) writes the row
  inside `transaction.atomic()`, and the transaction **commits** when the function
  returns. There is no compensating write, no abort endpoint, and no client-visible
  cancellation hook.
- The endpoint's own docstring says the save is idempotent: *"saving an event that is
  already saved returns the existing record."*

**So an `Esc` during an in-flight save cannot promise that the event was not saved.**
What it *can* promise is that the client stops showing "Saving…". The implementation is
therefore scoped exactly as the technical note instructs: **`Esc` resets the label to
`idle` and abandons the in-flight response.** If the request had already committed
server-side, the card is out of sync with the server — and the honest way to handle that
is to say so in the code and the comment, not to imply a guarantee the server does not
make. A follow-up is out of scope for this item (see *Not in this item*).

**The request is idempotent, so a duplicate is safe.** The technical note says this, and
it is why the in-flight guard is a `busy` flag rather than a request-id tracker.

## The two refusals, in the words the item fixes

**Criterion 5 — the cap.** Inline under the button:

> You've used your 1 free save today. Upgrade for unlimited.

with a `Text.Meta` "Upgrade" link.

**Criterion 6 — the clash.** Inline under the button:

> Conflicts with your saved dinner. Open Detail to resolve.

with a `Text.Meta` "Open" link to the event detail.

**Two sentences here are the item's, and two are not.** The criteria fix the sentences
verbatim, and this plan renders them verbatim. But the *server* also sends its own
sentence — `upgrade_hint`, "You saved one event today. Save more with Pro." — and
`lib/cap-details.ts` already reads it and `components/upgrade/upgrade-prompt.tsx` already
renders it.

**Which one wins?** The criterion is explicit and specific: *"renders inline under the
button: 'You've used your 1 free save today. Upgrade for unlimited.' with a Text.Meta
'Upgrade' link."* That is a *different* sentence from the server's `upgrade_hint`, and it
is the criterion's own. So the criterion's sentence is rendered, and the server's
`upgrade_hint` is **read but not rendered** — it stays available, and the criterion's
sentence is what the reader sees.

That is a real divergence from `UpgradePrompt`'s rule ("The sentence is the server's.
Rendered verbatim, never edited"), and it is deliberate: `UpgradePrompt` exists to render
a server's sentence where there is no criterion, and here the criterion *is* the sentence.
**The cap's number is also stated — "your 1 free save" — where `UpgradePrompt` deliberately
does not render `cap` at all.** The criterion names the number, so the number is there.

The plan records this as a deviation (#2 below) because it is a place where the item's
criterion and an existing house rule disagree, and the next reader needs to know which
one won and why.

**"1" and "dinner" are not hard-coded facts — they are the payload's.** "your 1 free
save" reads the `cap` from the refusal's `details.cap` (the server sends `cap: 1`), so
if the tier's ceiling ever changes, the sentence changes with it. "your saved dinner" is
the mockup's example, and the criterion fixes it verbatim; the *clashing* event's actual
name is available in `details.conflicts[0].other_side.name`, and the criterion does not
ask for it. The implementation renders the criterion's sentence and **does not read
`details.conflicts` at all** — the "Open" link points at this event's own detail page
(`/events/{slug}`), which is where the choice is made. The conflict detail is not carried
in the DOM, and nothing in the criterion requires it to be.

*(Corrected during the code review. This paragraph originally claimed the server's
conflict detail was "carried in the DOM for the 'Open' link's target", which the
implementation does not do. The AC asks for a link "to the event detail" — the event being
saved — and that is what the link does. The claim was the plan's, not the code's.)*

**Both refusals are inline, in the normal flow, under the button.** No `role="dialog"`, no
`aria-modal`, no overlay, no portal, no toast, no `position: fixed`. The item says this
twice — once in the description (*"never a modal, never a toast"*) and once as a
criterion — and the criterion demands a test. **The test asserts the absence by name:**
it queries for `[role="dialog"]`, `[aria-modal="true"]`, `[role="alertdialog"]`, and a
toast container, and fails if any exists. A test that only checked the *copy* would pass
while a modal appeared — which is exactly the failure this criterion names.

**The lines are `role="status"`, not `role="alert"`.** A refusal is information, not an
emergency; an assertive region would interrupt a screen reader mid-sentence. This is the
same decision `UpgradePrompt` documents.

## The button itself

**It is a real `<button type="button">`** (criterion 10) with
`aria-label="Save {event name} to my Pulse"`, and the **visible** label stays "Save".
The visible word is short because it sits on a card; the accessible name is long because
it must say which event, on a page with a dozen identical-looking buttons.

**The morph is announced (criterion 11).** `aria-live="polite"` on the button, and
**focus does not move** — the button keeps focus, so a keyboard user who pressed Enter
is still on the control they pressed. The announcement says what changed ("Saved to your
Pulse") and nothing more.

**The focus ring is 2px `color.accent.terracotta` at AA** (criterion 12) — the codebase's
`focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-accent-terracotta`
idiom, which `browse-card.tsx` already uses for the card link. **`Enter` and `Space` both
trigger the machine** — which is what a real `<button>` does, and the reason criterion 12
is satisfiable without a keydown handler: a `<div role="button">` would need one, and
would get the `Space` case wrong by default.

**The 240ms morph collapses under `prefers-reduced-motion: reduce`** (criterion 13). This
is the one place the plan reaches for an existing token rather than a new one:
`--motion-fade-in` is **`opacity 240ms ease-out`** (`tokens.css:154`) — the same 240ms the
criterion names — and `.fade-in` already collapses to `transition: none` under the
reduced-motion media query in `globals.css`.

**So the morph uses `.fade-in` and adds no new animation.** `tests/architecture.test.ts`
bans every `transition-*`/`duration-*`/`ease-*` class in a `.tsx`, so a hand-written
`transition-opacity duration-300` would fail the build; and `.fade-in` is the product's
only transition. The criterion's "240ms morph" and the product's "240ms fade" are the
same number, which is not a coincidence worth breaking the house rule over.

One caveat, stated honestly: `.fade-in` uses `@starting-style`, so it fades an element in
**when it first renders** — it is not a class-toggle transition. The *label swap* is what
changes, and the swap is instant in the DOM; `.fade-in` fades the label in as it mounts.
Under reduced motion the label swaps instantly, which is what criterion 13 asks for. The
plan does not claim a fade *between* labels that the CSS cannot produce.

## The request

**Exactly the existing endpoints** (criterion 4). No new endpoint, no new body:

```ts
await api.POST("/api/personal/saved-events/{catalog_event_id}", {
  params: { path: { catalog_event_id: eventId } },
});
await api.DELETE("/api/personal/saved-events/{catalog_event_id}", {
  params: { path: { catalog_event_id: eventId } },
});
```

This is `detail-actions.tsx:197`'s call shape exactly — no request body, no query
parameters. **The endpoint is reached only through the generated client** (`api` from
`@/lib/backend-client`), per AD-19; `frontend/lib/api/` is generated and is not
hand-edited, and `fetch` is banned in `components/` by the lint rule.

**The branch is on `code`, never on the message.** This is the technical note's first
sentence, and it is the rule `detail-actions.tsx` already follows:

```ts
const error = response.error;
const clash =
  response.response.status === 409 && error?.code === "scheduling_conflict"
    ? error.details?.conflicts?.[0]
    : undefined;
const capDetails = readCapDetails(error);
```

`readCapDetails()` branches on `code` too, against a `CAP_CODES` set that already
includes `save_cap_reached`. **A string match of the message would break the moment the
backend reworded a sentence** — and the backend owns the wording, so it will.

**The two branches are not symmetric, and that is the point.**

| Answer | The client does |
|---|---|
| 2xx | `saved` — the label morphs, the 1500ms lockout starts |
| 409 `scheduling_conflict` | `saved` **plus** the conflict line — **the save stands**; the button says "Saved ✓" and the inline line points at the detail screen |
| 409 `save_cap_reached` | `idle` **plus** the cap line — **the save did not happen**; the button says "Save" and the inline line points at the pricing page |
| anything else / a throw | `idle` plus a quiet failure line |

**A 409 clash is not a failed save.** The server wrote the row and *then* found the clash
(`api.py:398` — *"the save row exists, the pair is active, and the flow is waiting for a
choice"*). `detail-actions.tsx` already encodes this: *"A 409 is not a failed save… the
button reads 'Saved to your Pulse' and the prompt opens over it."* Browse does the same
thing in its own way: the button reads "Saved ✓", and the inline line — calm, in the flow,
not a modal — points at the detail screen where the conflict can be resolved.

**A cap is final, and is not retried.** `detail-actions.tsx`: *"A cap is a refusal, not a
failure, and it is final until the user upgrades. The save is not retried."* Same here.

**`unsave` is the DELETE, and it closes the conflict pairs.** The endpoint's own
description: *"The conflict pairs it took part in close as `cleared_by_state_change`."* So
the un-save needs no cleanup of its own — and the client must not invent any.

## What the island owns, and what it does not

**It owns:** the state machine, the two requests, the two refusal lines, the quota wall
and the announcement.

**It does not own:** the card's ranking, the tier split, the card's own facts, or the
quota's *meaning*. AD-10's rule — *"the page renders the payload and decides nothing"* —
applies here in one specific form: **the island does not decide whether a save is
allowed.** It renders the wall the payload states, and the server's gate is the gate. A
client-side refusal would be a second source of truth for a rule the server owns, and it
would be wrong for a Pro user whose `is_pro` flag had gone stale.
