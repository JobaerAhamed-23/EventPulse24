When an event changes underneath you

FR-58 is the user creating a conflict — present, acting, choosing. FR-55 is an event changing while nobody is there. Same visual conflict, entirely different moment. They share a surface because they share a record: both read the one CONFLICT_PAIR row that AD-21 makes the single source for every conflict indicator in the product.

A Cancelled, with nothing else affected FR-55 · "notified, removed from the digest"
✕Cancelled
✕
This event was cancelled

The organiser called it off. It's been taken out of your digest — nothing else of yours changed.

The card leaves the digest at the candidate stage, not by deleting a composed row — AD-10 keeps composed digest rows immutable. Reminders for it are cancelled with the save.

B Cancelled, and it clashed with something of yours FR-55 · "the personal event is preserved (no auto-cancel)"
✕Cancelled
✕
This event was cancelled

It's been taken out of your digest.

Dentist appointment — your own event, at the same time — is untouched and still on your calendar.

The clash between them is gone, because this event is. You didn't resolve anything — nothing is being asked of you, and this won't come back.

The hollow dot and dashed border are the point: AD-21 closes this pair as cleared_by_state_change, which is not a user resolution. A filled indicator or a "Resolved ✓" would congratulate the user for a decision they never made.

This is a live pair — filled amber dot, solid border — and it routes to the same Sheet.ConflictResolution FR-58 uses, with the same three actions. The message names the other event rather than saying "another event", which is FR-55's "[other event]".

D The per-event mute — and why it is not silence FR-55 · "mute state-change notifications for a specific event"

Not muted

The label says what pressing it does.

Muted

The label changes to say what is true, so a user can tell they have muted it without reading the state of a widget. A toggle whose label never changes cannot do that.

A muted event, cancelled — the banner still shows

✕Cancelled
✕
This event was cancelled

It's been taken out of your digest.

…and a cancellation still gets through.

The rule is not "muted means silent". The backend raises a cancelled or superseded notice despite the mute, and says why: "FR-55 has already removed the event from their digest, so silence about it is the one failure with no second channel to catch it." The mute silences the corrections that have another way of reaching the user — a moved time, a moved venue, a sold-out — and leaves the one that does not.

The API reports muted and notice as two independent facts; the client decides what the mute reaches. A read that suppressed the notice whenever muted was true would make this rule impossible to honour.

E One surface, two triggers the acknowledgment the matrix found missing

FR-58 — the user acts

The user creates or edits an event that clashes. They are present and choosing, so the prompt requires an explicit choice — there is no dismiss-without-resolution.

FR-55 — the event changes

An organiser cancels, postpones or moves. Nobody is present and nobody chose. So the surface informs first, and only offers the choice when a live overlap remains.
