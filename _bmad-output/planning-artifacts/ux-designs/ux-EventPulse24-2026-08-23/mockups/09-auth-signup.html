States

Three render states per component.input.field.error. State A (above) is the rendered default — fresh form, all fields valid, primary enabled.

State B — Passwords don't match cross-field validation

The only cross-field validation on this surface. The error renders beneath the Confirm field (the one the user is filling); the Password field stays valid (don't blame the first input after the user already typed it correctly).

Passwords don't match. 
// cross-field validation runs on Confirm blur AND on form submit
if (signup-password.value !== signup-password-confirm.value) {
  confirmField.classList.add('has-error');
  confirmField.querySelector('.field-error .text').textContent
    = "Passwords don't match.";
  confirmField.querySelector('input').setAttribute('aria-invalid', 'true');
}

// ENGINEERING NOTE: the Password field's value is NOT cleared on mismatch.
// The user already typed it correctly; clearing it would be unkind.

State C — Email already exists server-side error + ghost link to /signin

Server-side 409 conflict. Per the soft-wall pattern, the email field carries the error AND the inline ghost link routes the user to /signin — don't make them start over.

An account with that email already exists. Sign in → 
server returns 409 Conflict on POST /api/signup
  → .field.has-error applied to email field
  → .field-error renders inline: "An account with that email
    already exists. Sign in →" with the ghost link
  → role="alert" announces to screen readers
  → Password fields stay intact (don't clear them; user
    may have started typing + scrolled past the error)

exception to the account-enumeration rule: SIGNUP is opt-in
registration, so revealing "this email is taken" is acceptable
(it actually helps the user recover). The enumeration guard
applies to SIGNIN, where attackers probe for valid emails.

Success transition copy-locked · visual deferred

Submit succeeds → primary CTA morphs to spinner + "Creating account…" (mirrors Component.Auth.SignIn State C). On 200 OK, the form morphs to a single inline notice: "Account created. Taking you to onboarding…" with a 1.5s hold, then location.href = '/onboarding'. OAuth providers skip onboarding-step1 entirely — their calendar was auto-attached during the handshake.

submit → POST /api/signup → 200 OK
  → single Text.Meta inline notice: "Account created. Taking you
    to onboarding…"
  → 1500ms hold (prefers-reduced-motion: 0ms)
  → location.href = '/onboarding' (step 1 calendar connect)
  → OAuth users: skip step 1 entirely (auto-connect already done)

post-signup flow stays within FR-1's ≤3 user-visible steps:
  OAuth users: 0 calendar steps (auto-skip) + interests + digest time = 3
  Email/password users: calendar connect + interests + digest time = 3
  Both routes reach the first Pulse Digest in ≤30s as required.
